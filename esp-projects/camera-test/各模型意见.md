## 一、急弯/直角弯无法有效转向（主要漏洞）

### 问题描述
- **当前状态机**中，`CORNER` 状态**仅由分支检测（`branch_hint`）触发**，用于处理岔路（T/Y型）。对于连续弯道，线不会“消失”或出现分支，因此永远不会进入 `CORNER` 状态。
- 在 `NORMAL` 状态下，**转向输出被 `LINE_PID_TURN_MAX = 10` 严格限制**，即使 `heading_error` 很大，输出最大也只有 10（对应于约 10% 的 PWM 占空比）。对于直角弯，这样的转向力矩通常不足，导致小车冲出赛道。

### 改进建议
1. **增加急弯检测机制**  
   当 `heading_error` 的绝对值大于某一阈值（例如 40~50）且持续 2~3 帧时，判定为急弯，**临时提高转向上限**（例如提高至 25~30）并降低速度（保持 CRAWL）。  
   ```c
   if (abs(observation.heading_error) > 45 && s_state == LINE_STATE_NORMAL) {
       int turn = clamp_int(pd_output, 25); // 临时放开限制
       drive(LINE_FORWARD_CRAWL, turn);
       // 可记录急弯状态，避免频繁切换
   }
   ```

2. **增大 `LINE_PID_TURN_MAX`**  
   将 `#define LINE_PID_TURN_MAX 10` 改为更大的值（如 `25` 或 `30`），并配合实际电机测试，确保转向力度足够。

3. **考虑使用“预瞄”转向增强**  
   若 `heading_error` 已经很大，说明前方线急剧弯曲，可以令转向输出与 `heading_error` 成正比（前馈项权重可调），而非全部依赖 PD 限幅。

---

## 二、分支检测误用于弯道

### 问题描述
`branch_hint` 函数在底部附近扫描特定行，寻找与中心偏移较大的连续黑段，并累计命中次数。这种方式**容易将急剧弯曲的线误判为分支**，但实际并不会触发 `CORNER`（因为无分支），反而可能使 `pending_turn` 被错误设置，一旦旧线消失进入 `CORNER`，会向错误方向转弯。

### 改进建议
- 在 `NORMAL` 状态下，若检测到 `heading_error` 突然增大，**优先使用急弯模式**，而不是依赖分支检测。
- 可以**增加“弯道模式”**，当 `lateral_error` 和 `heading_error` 方向一致且幅度较大时，直接进入弯道转向，放弃分支检测逻辑。

---

## 三、丢失检测过于敏感

### 问题描述
- 一旦 `observe_line` 返回 `candidate = false`，**立即进入 `LOST` 状态**，并重置 PD 滤波器。在弯道中，线可能因为光线或视角瞬间消失一帧，导致状态抖动，重捕获过程可能产生不必要的减速和方向摆动。
- 当前没有对连续丢失帧数做容忍，导致控制不连续。

### 改进建议
- 增加一个**丢失容忍计数器**：当 `candidate` 为 `false` 时，不立即进入 `LOST`，而是保持当前转向指令，并扩大搜索窗口（利用 `lost_frames` 膨胀）尝试重捕获，**连续 2~3 帧均丢失**才真正进入 `LOST`。
- 在 `LOST` 状态下，重捕获确认需要连续 2 帧（已有 `LINE_REACQUIRE_CONFIRM_FRAMES`），但重捕获窗口固定围绕最后种子，可能限制灵活性。可以考虑根据最后有效的 `heading_error` 方向，允许窗口向该方向偏移。

---

## 四、ROI 范围固定，不利于急弯

### 问题描述
- ROI 横向限制为 **20%~80%**（即仅图像中间 60%），纵向去除顶部 30%。对于直角弯，线会迅速偏移到图像边缘，可能跑出 ROI 导致丢失，即使仍在视野内。

### 改进建议
- 适当**扩大 ROI 横向范围**（例如左右各保留 10%），或者**动态调整 ROI**：当检测到线接近边缘时，暂时放宽 ROI 边界。
- 注意底部保留的 `LINE_BOTTOM_SKIP_ROWS` 已预留，但可进一步将顶部裁剪从 30% 降低到 20%，让更多前方路面进入视野。

---

## 五、速度与转向的配合

### 问题描述
- 当前速度根据 `lateral_error` 大小分档，急弯时速度会降至 `LINE_FORWARD_CRAWL = 17`（17% PWM），配合 10% 转向可能仍显不足。
- 若转向上限提高，速度可适当提高，但需平衡抓地力。

### 改进建议
- 在急弯检测触发时，强制速度为 `LINE_FORWARD_CRAWL`（或更低），转向使用最大输出。
- 直线段可维持较快速度（`LINE_FORWARD_FAST = 30`），提高比赛效率。

---

## 六、关于“只看近点”的疑问

### 当前策略
- 代码同时使用了**近点（`lateral_error`）和远点（`heading_error`）**，其中 `heading_error` 反映线的倾斜趋势，相当于预瞄。这种设计在弯道前可以提前转向，有助于减少过冲。
- 如果出现“过早转向”现象，通常是因为**远点窗口太远**（当前取顶部 4 行，即约离底部 65%~92% 高度），或者 `KH` 权重过大。

### 调整建议
- **减小 `LINE_NEAR_TOP_PERCENT` 和 `LINE_NEAR_BOTTOM_PERCENT`** 以缩小远点窗口，使预瞄点更靠近车体。
- **降低 `LINE_PID_KH` 的值**（当前为 8），减小前馈项的影响。
- 或者，**根据速度动态调整远点距离**：速度快时看得远，速度慢时看得近，但此工程实现较复杂。

## KiMi：

你的直觉非常准——**三轮小车每一 tick 确实应该优先以「近点」作为转向依据，远点只适合做速度规划或状态预判，而不应该直接参与当前 tick 的转向角计算**。你现在代码里的 `heading_error`（远点-近点差值）在直线段是有效前馈，但在锐角弯/直角弯里会提前把转向角拉向切线外侧，导致「还没入弯就提前转向」或「入弯后转向过度甩出赛道」。

下面按**致命/高危/优化**三级，把当前代码里影响循线稳定性的核心漏洞逐条列出，并给出可直接落地的修改建议。

## 一、致命级：前瞻(heading)策略在急弯中的反作用

### 1. 远点前馈在弯道中给出反向/过量修正
**位置**：`camera_line_follow.c`：`track_line()` → `observation->heading_error`；`pd_steering()`

```c
// 当前逻辑：远点与近点的误差差作为前馈
observation->heading_error = line_error(near_center, width) -
                             line_error(far_center, width);

// PD 中直接减去 heading_error
int target = (LINE_PID_KP * s_tracking_error -
              LINE_PID_KH * heading_error -
              LINE_PID_KD * delta_lateral_error) / LINE_PID_SCALE;
```

**问题**：  
- 入锐角弯时，远点很快会偏离到赛道切线方向甚至完全丢失。此时 `heading_error` 可能突然变大，PID 会把它当成「车头偏角」来做前馈补偿。  
- 三轮小车当前 tick 的横向偏差其实只由**近点**决定，远点反映的是「0.5 秒后的未来偏差」。用未来偏差修正现在，等于提前打方向，在锐角弯处必然切出内道或撞外侧。

**修复建议**：  
把 `heading_error` 的权重做成**动态衰减**。横向偏差越大（说明正在急弯），越不相信远点。

```c
// 在 pd_steering() 中增加动态 KH
int kh = LINE_PID_KH;
if (abs(lateral_error) > LINE_ERROR_MEDIUM) {
    kh = 0;  // 急弯时完全关闭远点前馈
} else if (abs(lateral_error) > LINE_ERROR_DEADBAND) {
    kh = LINE_PID_KH / 2;
}
int target = (LINE_PID_KP * s_tracking_error -
              kh * heading_error -
              LINE_PID_KD * delta_lateral_error) / LINE_PID_SCALE;
```

### 2. 近点窗口仍然太高，「近点」不够近
**位置**：`LINE_NEAR_TOP_PERCENT 65`、`LINE_NEAR_BOTTOM_PERCENT 92`

当前「近点」覆盖了画面底部 27%（约 65 行），对于 240p 画面来说，这相当于看前方 20~30cm。三轮小车轴距短，**真正决定当前 tick 是否压线的应该是画面最底部 5~8cm 的线段**。

**修复建议**：  
把近点窗口压到更底部，让「近点」真的够近。

```c
#define LINE_NEAR_TOP_PERCENT    85   // 只看底部 15%
#define LINE_NEAR_BOTTOM_PERCENT 100
#define LINE_BOTTOM_SKIP_ROWS    0    // 最底行往往有畸变，但 skip 1 行即可
```

如果你担心画面最底部有镜头畸变或车体遮挡，可以保留 `LINE_BOTTOM_SKIP_ROWS 1`，但 `TOP` 一定要抬高到 80~85。

## 二、高危级：状态机与种子点脆弱

### 3. LOST → NORMAL 重捕获条件过于依赖「旧种子」横向位置
**位置**：`camera_line_follow_process_frame()` → `LINE_STATE_LOST` 分支

```c
const bool near_last_seed =
    abs(observation.seed_x - s_seed_x) <= confirm_window;
if (!near_last_seed) {
    s_reacquire_frames = 0;  // 一朝偏离，全部清零
}
```

**问题**：  
- 在直角弯中丢失后，小车已经转了一部分弯，黑线实际上已经横向移动到了画面另一侧。此时如果还强制要求候选点必须靠近「丢失前的旧种子」，就永远恢复不了。  
- 三轮小车在弯道中横向位移是连续的，但种子坐标却卡死在入弯前。

**修复建议**：  
LOST 重捕获时，种子窗口应**随丢失时间逐步扩大**，并允许围绕画面中心做扇形搜索，而不是死锁在 `s_seed_x`。

```c
// LOST 状态下，搜索中心逐渐从旧种子移向画面中心
int search_center = s_seed_x;
int lost_age = (int)s_lost_frames;
if (lost_age > 10) {
    search_center = (s_seed_x + (int)width / 2) / 2;
}
if (lost_age > 30) {
    search_center = (int)width / 2;
}
// 然后把 search_center 传给 track_line 的 seed，而不是直接用 s_seed_x
```

---

### 4. 种子点 `s_seed_x` 没有低通滤波，单帧噪声即可跳变
**位置**：`update_seed()`

```c
static void update_seed(const line_observation_t *observation)
{
    s_seed_x = observation->seed_x;  // 直接硬赋值
    s_seed_valid = true;
}
```

**问题**：  
- 如果某帧地面反光、阴影或赛道边缘被误判为线，`seed_x` 会瞬间跳到错误位置，下一帧的搜索窗口就会跟着跑偏，极易诱发 LOST。

**修复建议**：  
给种子加一个一阶低通滤波（类似你 threshold 的滤波方式）。

```c
#define SEED_FILTER_OLD  3
#define SEED_FILTER_NEW  1

static void update_seed(const line_observation_t *observation)
{
    if (!s_seed_valid) {
        s_seed_x = observation->seed_x;
        s_seed_valid = true;
        return;
    }
    s_seed_x = (s_seed_x * SEED_FILTER_OLD +
                observation->seed_x * SEED_FILTER_NEW) /
               (SEED_FILTER_OLD + SEED_FILTER_NEW);
}
```

### 5. branch_hint 在弯道中极易误触发，导致提前进入 CORNER
**位置**：`branch_hint()`；`update_turn_memory()`

```c
const int offset = positive_percent((int)width, LINE_BRANCH_OFFSET_PERCENT,
                                    LINE_SEARCH_HALF_MIN * 2);
```

**问题**：  
- 弯道本身就会导致线从底部到顶部产生自然横向偏移。`branch_hint` 在底部几行横向搜索，很容易把「弯道的弧线」当成「分叉的另一条线」。  
- 一旦 `s_pending_turn` 被置为 ±1，旧线一消失就会进入 `CORNER` 状态，以固定转角 `LINE_TURN_MAX` 做盲拐。如果这是误判，小车就直接冲出赛道。

**修复建议**：  
**在横向误差较大时禁止 branch 检测**。弯道和分支不会同时发生：如果你已经在弯道里（`abs(lateral_error) > LINE_ERROR_MEDIUM`），就不应该再检测分支。

```c
static void update_turn_memory(const line_observation_t *observation)
{
    // 新增：大横向误差时，认为是弯道而非分支
    if (abs(observation->lateral_error) > LINE_ERROR_MEDIUM) {
        s_hint_direction = 0;
        s_hint_frames = 0;
        return;
    }
    // ... 原有逻辑
}
```

### 6. CORNER 状态的退出条件太理想化，直角弯容易超时
**位置**：`LINE_STATE_CORNER` 分支

```c
if (direction_of(displacement) != s_pending_turn ||
    abs(displacement) < minimum_shift ||
    abs(observation.seed_x - s_corner_predicted_x) > prediction_window) {
    new_line_candidate = false;
}
```

**问题**：  
- `s_corner_predicted_x` 是线性外推：`origin_x + turn * step * corner_frames`。真实小车转弯是圆弧，不是直线。  
- 在直角弯中，新线往往不会出现在线性预测的位置，导致 `corner_exit_frames` 一直攒不够，最终触发 `LINE_CORNER_TIMEOUT_MS`（3 秒）后 `disarm_tracking()` 停车。

**修复建议**：  
- **放宽预测窗口**：`prediction_window` 在弯道持续期间应随时间扩大。  
- **或者更简单地**：CORNER 状态不要依赖预测位置，而是围绕「画面中心 ± 一个较大窗口」搜索黑线，找到即视为退出。

```c
// CORNER 时，搜索窗口逐渐放大，中心固定在画面中心（或最后已知方向侧）
int corner_half = positive_percent((int)width,
                                   LINE_CORNER_WINDOW_START_PERCENT +
                                   (int)s_corner_frames * LINE_CORNER_WINDOW_GROW_PERCENT,
                                   LINE_SEARCH_HALF_MIN);
// 搜索中心改为画面中心，而不是 s_corner_predicted_x
int corner_center = (int)width / 2;
if (s_pending_turn > 0) corner_center = (int)width * 60 / 100;  // 偏右寻线
if (s_pending_turn < 0) corner_center = (int)width * 40 / 100;  // 偏左寻线
```

## 三、优化级：电机控制与参数适配

### 7. 正常循线时最大转向角 `LINE_PID_TURN_MAX 10` 可能不足以应对直角弯
**位置**：`pd_steering()` → `clamp_int(target, LINE_PID_TURN_MAX)`

**问题**：  
- `LINE_TURN_MAX 19` 仅在 `CORNER` 状态使用，而 `NORMAL` 状态被限制在 10。  
- 对于三轮小车，如果 B 轮是转向轮，10/100 的占空比（实际约 10% 电机输出）可能根本转不动。直角弯需要 NORMAL 状态下也能输出较大转角。

**修复建议**：  
把 `LINE_PID_TURN_MAX` 提高到 15~18，或者做成动态：误差越大，允许的最大转向越大。

```c
int dynamic_turn_max = LINE_PID_TURN_MAX;
if (abs(lateral_error) > LINE_ERROR_LARGE) {
    dynamic_turn_max = LINE_TURN_MAX;  // 大误差时允许 CORNER 级转向
}
target = clamp_int(target, dynamic_turn_max);
```

---

### 8. LOST 时的「直走」策略在弯道中等于自杀
**位置**：`LINE_STATE_LOST` 分支

```c
if (lost_us <= (int64_t)LINE_LOST_HOLD_MS * 1000) {
    drive(LINE_FORWARD_CRAWL, 0);  // 直走！
}
```

**问题**：  
- 弯道中一旦 LOST，小车如果保持 `LINE_FORWARD_CRAWL` 直走 300ms，必然冲出弯道切线。

**修复建议**：  
LOST 时应该**减速并做微幅扫线**（wiggle），而不是直走。利用三轮结构，让小车在原地做小角度左右摆动，增加重捕获概率。

```c
if (lost_us <= (int64_t)LINE_LOST_HOLD_MS * 1000) {
    int wiggle = ((int)s_lost_frames % 20 < 10) ? 3 : -3;  // 轻微左右扫线
    drive(LINE_FORWARD_CRAWL / 2, wiggle);  // 减速+扫线
} else {
    zero_motor_outputs();
}
```

### 9. 启动 ramp 期间遇到急弯可能因 output_limit 受限而转不过弯
**位置**：`motor_set()` → `s_motor_start_ramp_frames`

```c
output_limit = LINE_MOTOR_START_MIN_OUTPUT +
               ((MAX_OUTPUT - LINE_MOTOR_START_MIN_OUTPUT) * elapsed) /
               LINE_MOTOR_START_RAMP_FRAMES;
```

**问题**：  
- 启动后前 18 帧（约 0.6s）电机输出被限制在 12→34 线性上升。如果起点就在直角弯上，此时 `output_limit` 会钳制 `turn`，导致转向不足。

**修复建议**：  
ramp 只限制 `forward`，不限制 `turn`。转向响应在启动时必须满功率可用。

```c
// 在 motor_set 中，B 轮（转向轮）不受 ramp 限制
int output_limit = MAX_OUTPUT;
if (s_motor_start_ramp_frames > 0 && motor->channel != LEDC_CHANNEL_1) {
    // 只限制 A/D 前进轮
    ...
}
```

### 10. 摄像头镜像 `CAMERA_LINE_MIRROR_X` 与实车安装
**位置**：`CAMERA_LINE_MIRROR_X 0`

**问题**：  
- 如果摄像头装反（镜头朝后或旋转 180°），左右会完全颠倒，所有 turn 方向都会反向。这在实车调试中极其常见。

**建议**：

## 四、总结：针对「只看近点」的推荐架构

你提出的「只看近点」是三轮短轴距小车循线的**黄金法则**。建议把控制逻辑改成这样：

| 层级          | 作用               | 实现                                                         |
| ------------- | ------------------ | ------------------------------------------------------------ |
| **近点 PD**   | 当前 tick 的转向角 | 只用画面底部 10~15% 的线段中心计算 `lateral_error`，做 PD 闭环 |
| **远点预判**  | 入弯减速/状态切换  | 远点仅用于判断「前方是否是急弯」。若远点横向偏移大，提前把 `forward` 降到 `LINE_FORWARD_SLOW/CRAWL`，但不直接参与 turn 计算 |
| **动态 KH**   | 消除远点干扰       | `abs(lateral_error) > MEDIUM` 时 `KH=0`，直线时 `KH` 恢复    |
| **种子滤波**  | 防止单帧跳变       | 对 `seed_x` 做一阶滤波                                       |
| **LOST 扫线** | 提高恢复率         | 丢失后不做直线盲走，做微幅左右摆动                           |

# ESP32‑S3 三轮巡线代码漏洞分析 & 问题根源

> 硬件：ESP32‑S3‑WROOM‑2，三轮小车（A/D左右驱动轮，B后轮舵轮/差速辅助，TB6612驱动）；摄像头UVC输出MJPEG，解码RGB565；ST7735做调试屏幕。 核心痛点：**现在代码同时使用近处点（near_center）+远处点（far_center）生成lateral_error + heading_error做PD控制**，`heading_error`来自图像上方（远处赛道），会造成**过早转向**；同时还有抗干扰、状态机、观测、电机、阈值、时序一系列隐性漏洞。

先回顾现有关键逻辑：

```
// camera_line_follow.c
const int near_center = average_points(points, 0, near_count);   // 图像底部，离车最近
const int far_center = average_points(points, point_count - far_count, far_count); // 图像上方，远处
observation->lateral_error = line_error(near_center, width);
observation->heading_error = line_error(near_center, width) - line_error(far_center, width);

// PD控制器
int target = (LINE_PID_KP * s_tracking_error - LINE_PID_KH * heading_error - LINE_PID_KD * delta_lateral_error) / LINE_PID_SCALE;
```

- `near_center`：points数组下标0，对应图像最底部扫描行，**真实最近的赛道点**
- `far_center`：points数组末尾，图像靠上，代表摄像头视野里远处赛道
- `heading_error`：远近误差差，用来预判赛道倾斜。**锐角/直角弯场景，这个远处信息会让小车提前打方向，还没到弯道就开始拐，走线内缩、冲线。**

## 一、控制算法核心漏洞（最高优先级：过早转向根源）

### 漏洞1：heading_error（远处前瞻项）参与闭环PD，弯道过早转向

**现象**：直线正常；看到远处弯道，还没行驶到弯道位置，小车就开始打转向，切入弯道过早，容易冲出黑线；锐角弯尤其明显。

> 你的理解是正确：**每一帧(tick)决策应该优先信任近处（图像底部）的黑线位置；远处只做预测提示，不能直接参与实时转向输出。**

现在代码：

1. `Kh * heading_error`直接叠加到转向输出；远处赛道一倾斜立刻输出转向。
2. 直角/锐角弯道：图像上方先出现弯道，底部黑线还在中心，控制器已经输出大转向，小车提前拐。

区分两个概念：

- ✅近处点（near_center）：**唯一用来计算当前横向偏移，用于真实转向输出**。
- ⚠️远处点（far_center）：**只适合做预判（支路检测、预提示即将来弯），不应该直接加到PD输出**。

> 当前代码`branch_hint()`函数已经利用上面扫描点做支路预判生成`pending_turn`，这个是状态机层面的预判；但是`heading_error`又把远处倾斜直接塞进PD闭环，双重前瞻，造成过早早转。

### 漏洞2：PD没有积分项，大偏移下稳态误差；但是加积分又会带来弯道超调

当前PD：P‑横向误差，D‑横向误差微分，H‑heading前馈；**无I积分**。

- 轻微偏移直线，会有静态偏差，小车会小幅蛇形。
- 但是不能简单直接加I：弯道时积分会累积大误差，出弯超调。需要条件积分（只有直线状态才启用积分，CORNER/LOST状态关闭积分）。

### 漏洞3：速度逻辑只根据横向误差绝对值，没有抑制弯道速度

`forward_speed()`只看`abs(lateral_error)`。直角/锐角进入CORNER状态，虽然设置`LINE_FORWARD_CRAWL`爬行，但是**NORMAL状态下刚识别到弯道支路还没切CORNER状态时速度仍然跑中高速**，高速下转向响应跟不上，容易飞线。

### 漏洞4：转向输出slew限制太弱，帧间变化限制`LINE_PID_SLEW_PER_FRAME=2`

帧间隔受USB摄像头帧率波动（10‑30fps浮动），固定每帧最大变化量，帧率低的时候两帧间隔时间长，转向变化量太小，弯道转不过来。应该改为**时间归一化限制，而不是帧归一化**。

## 二、图像检测与抗干扰漏洞（截断周边干扰目标）

> 代码已经设置ROI `LINE_ROI_LEFT_PERCENT=20`、`LINE_ROI_RIGHT_PERCENT=80`、`LINE_ROI_TOP_PERCENT=30`，裁剪画面四周，但是仍有漏洞。

### 漏洞5：ROI只裁剪统计区域，但是`scan_segment`搜索窗口在CORNER/LOST状态会大幅向外扩张

```
// track_line()
if (s_state == LINE_STATE_CORNER) {
    search_percent = LINE_CORNER_WINDOW_START_PERCENT + (int)s_corner_frames * LINE_CORNER_WINDOW_GROW_PERCENT;
} else if (s_state == LINE_STATE_LOST) {
    const int extra = (int)(s_lost_frames * LINE_LOST_WINDOW_GROW_PERCENT);
    search_percent += extra;
}
```

- CORNER、LOST状态搜索窗口不断扩大，超出20‑80%ROI，会抓到赛道外阴影、桌椅、地面裂纹，造成误识别黑线。
- 虽然`scan_segment`内部有`roi_left / roi_right`，但是**窗口放大逻辑容易越界触发异常线段匹配**。

> 修复约束：**无论什么状态，scan_segment的左右搜索边界硬限制在 ROI_LEFT ~ ROI_RIGHT，搜索half_window只允许在这个区间内扩展，不能超出**。

### 漏洞6：自适应阈值完全依赖ROI统计，局部强光/局部阴影单帧阈值跳变

`calculate_binary_threshold()`只取固定ROI区域直方图，地面局部光斑，阈值剧烈跳动，黑白分割错乱，黑线识别断裂。

- 当前有`filter_binary_threshold()`做低通滤波限制`slew=8`，但是单帧强光冲击依然会跳变。
- 缺少阈值上下限保护，虽然有宏定义`THRESHOLD_MIN/MAX`，但是对比度不足直接返回0，触发candidate失效小车进入LOST。

### 漏洞7：`scan_segment`线段匹配逻辑对锐角弯的斜向黑线识别不稳定

扫描是**水平逐行扫描**，对接近垂直的锐角弯道黑线，同一行黑像素占比很小，容易被判定为无效线段，`valid_rows`直接掉下去，小车进入LOST。

> 当前是固定`LINE_ROW_STEP=4`隔行扫描，追求实时性；大角度斜线，水平扫描很难抓取完整线段。

### 漏洞8：镜像宏 `CAMERA_LINE_MIRROR_X=0`硬编码

如果摄像头物理安装左右翻转，只改这一处；但是代码多处误差计算依赖这个宏，调试容易遗忘。

### 漏洞9：Finish停止条逻辑容易误触发

宽黑线判定`finish_candidate`，赛道上粗黑线弯道有可能误识别为终点停止条。

## 三、状态机逻辑漏洞（NORMAL / CORNER / LOST）

### 漏洞10：CORNER拐角状态完全依靠时间超时 `LINE_CORNER_TIMEOUT_MS=3000`，缺少位置反馈退出

进入CORNER拐角之后，小车只固定往记忆方向爬行转向`drive(LINE_FORWARD_CRAWL, -s_pending_turn * LINE_TURN_MAX)`，**不使用PD闭环**。

> 行为：直角/锐角弯阶段，小车固定打死方向爬行，盲弯。只有当新黑线跳到预测窗口才切回NORMAL。 如果地面干扰导致拐角阶段识别不到新黑线，直接超时disarm停车。锐角弯场景很容易发生。 理想改进：CORNER状态不要完全丢弃PD，允许使用近处`near_center`做有限修正，不是无脑固定打满方向。

### 漏洞11：支路检测`branch_hint()`容易误触发分支

`branch_hint()`用来预判即将到来的弯道生成`pending_turn`。依靠附近两行偏移检测分支；地面污渍、阴影会误检测出虚拟支路，错误进入CORNER拐角模式。

- 当前确认帧`LINE_BRANCH_CONFIRM_FRAMES=3`；但是光照变化下依然会误触发。缺少分支距离限制，远处微弱干扰就判定支路。

### 漏洞12：LOST丢失状态重捕获逻辑依赖`seed_x`，一旦seed被污染很难恢复

LOST状态只能在旧seed附近找黑线；如果某一帧误识别到旁边干扰物更新`seed_x`，后续会一直盯着干扰物，彻底丢失真实赛道。

### 漏洞13：arm上电解锁条件

上电之后需要`LINE_START_DELAY_MS=600`+连续3帧有效candidate才解锁电机。如果刚上电光线闪烁，解锁很慢。但是这个属于安全特性，不是bug。

### 漏洞14：看门狗超时`LINE_FRAME_TIMEOUT_MS=1200`

摄像头USB卡顿、丢帧，超过1.2s没有解码帧，直接disarm停车。高速移动场景USB UVC很容易出现帧抖动误停车。

## 四、电机与混控漏洞（三轮小车A/D驱动轮 + B舵轮）

```
static void drive(int forward, int turn)
{
    s_command_a = clamp_int(-forward - turn, MAX_OUTPUT);
    s_command_b = clamp_int(turn, MAX_OUTPUT);
    s_command_d = clamp_int(forward - turn, MAX_OUTPUT);
}
```

### 漏洞15：混控模型假设和真实三轮机械匹配风险

- A、D是左右驱动轮；B后轮作为转向辅助轮。

  > 当前混控公式：直行A=-forward，D=forward；turn叠加到A、D，B输出turn。 不同物理安装B轮的机械特性不一样：如果B轮是被动万向轮，**B输出PWM完全无效**，B电机不应该参与驱动；如果B是主动舵轮，当前混控公式不一定符合阿克曼/差速模型。 很多三轮小车B是万向从动轮，此时`s_command_b`输出PWM没有任何作用，反而浪费LED通道。

### 漏洞16：电机启动kick冲量、ramp斜坡

启动斜坡`LINE_MOTOR_START_RAMP_FRAMES`，换向kick脉冲；但是CORNER状态进入爬行模式没有kick，低速TB6612‑电机静摩擦大，轮子可能堵转不动。

### 漏洞17：MAX_OUTPUT=34，速度上限很低

所有速度都是百分比0‑34；虽然防止飞车，但是CORNER爬行速度`LINE_FORWARD_CRAWL=17`，地面阻力大容易动力不足。

### 漏洞18：STBY待机逻辑

armed=0的时候STBY拉低，TB6612硬件休眠；但是状态切换时序，状态机disarm立刻切断STBY，弯道过程一旦识别异常电机瞬间休眠，直接抱死。

# 针对性修改方案（重点解决【过早转向】，优先修改）

## 修改1：消除heading_error直接参与PD闭环（根治过早转向）

> 设计原则：**近处点near_center负责真实转向输出；远处far_center只用来做支路预判，禁止直接驱动转向**

### 方案A（推荐最小改动）

1. `track_line()`依然计算`heading_error`，但是**不再传入PD控制器做转向输出**。
2. PD只使用横向误差`lateral_error` + 横向误差微分项。

```
// pd_steering函数修改，移除heading_error输入
static int pd_steering(int lateral_error)
{
    // ...只对lateral_error做滤波P+D，删除Kh项
}
```

1. `heading_error`保留，仅作为**支路检测branch_hint的辅助提示量**，只影响状态机`pending_turn`，不直接输出电机转向。

> 效果：只有图像底部真实黑线偏移才会让小车转向；图像远处弯道只能触发pending_turn记忆，小车继续直行，**物理行驶到达弯道位置（黑线底部偏移）之后才会真正转向**，解决过早转弯。

> 注意：移除heading前馈之后，弯道响应会变慢，适当调大`LINE_PID_KP`补偿。

### 方案B（折中方案，保留有限前瞻）

仍然保留heading_error，但是**NORMAL状态下大幅衰减Kh；CORNER状态Kh直接置0**，不要完全删除。

```
int heading_comp = s_state == LINE_STATE_NORMAL ? (LINE_PID_KH * heading_error)/4 : 0;
int target = (LINE_PID_KP * s_tracking_error - heading_comp - LINE_PID_KD * delta_lateral_error) / LINE_PID_SCALE;
```

## 修改2：CORNER拐角状态不要完全盲打固定转向

原来CORNER状态：无脑固定`drive(LINE_FORWARD_CRAWL, -s_pending_turn * LINE_TURN_MAX);` 改为：CORNER状态仍然读取`near_center`近处黑线，如果能看到近处黑线，允许PD小幅度修正转向，只有完全看不到candidate，才使用固定死方向。

> 解决锐角弯盲拐冲出赛道。

## 修改3：硬限制所有状态下scan_segment搜索窗口，不能超出ROI边界

`scan_segment()`不管窗口参数怎么放大，left/right强制钳位在：

```
const int roi_left = (int)width * LINE_ROI_LEFT_PERCENT / 100;
const int roi_right = ((int)width * LINE_ROI_RIGHT_PERCENT / 100) - 1;
left = MAX(left, roi_left);
right = MIN(right, roi_right);
```

彻底截断画面左右干扰物体。

## 修改4：速度策略优化

1. 当`pending_turn !=0`（预判前方有弯，NORMAL状态），强制降低直行速度，不要跑FAST。
2. CORNER状态保持CRAWL低速。
3. 只有正常直线、误差很小的时候跑FAST。

## 修改5：条件积分PD（可选，改善直线稳态）

仅当`s_state == LINE_STATE_NORMAL && observation->confidence很高`才启用积分；LOST、CORNER、大误差下积分清零，防止弯道积分饱和超调。

## 修改6：支路检测增加距离约束

`branch_hint()`检测分支的时候，**只允许图像中下部（近处）的分支才判定pending_turn；图像上方远处检测到分支忽略**，避免远处图像边角阴影误判弯道。

## 修改7：电机B轮适配

如果你的三轮小车B是万向从动轮，所有`motor_set(&motor_b, xxx)`输出直接置0，B电机不再输出，消除无效混控。

# 总结核心根源

> 你提的关键点完全正确：小车每一步决策，控制权应该交给**摄像头画面底部（离车最近）黑线位置**；画面上方远处只能做预判提示，**不能直接参与实时转向输出**。现在代码把远近两者都送入PD闭环，这就是锐角/直角弯过早转向的主因。 其余漏洞是抗干扰、状态机盲拐、搜索窗口溢出、电机混控等次要问题。



## Gemini：

### 关于“近点与远点”的判断策略

**仅看近点会导致车体震荡并错过急弯，但将远点直接混入 PID 转向控制必然导致过早转向（内切拉线）。**

- **近点（车头正前方 ROI 下半部）**：表征**当前横向位置偏差（$e_y$）**。只看近点时，系统缺乏阻尼和前瞻预判，直道提速极易蛇形画龙，遇到直角/锐角弯时会因反应滞后直接冲出赛道。
- **远点（ROI 上半部 / 前瞻视野）**：表征**道路走向与曲率变化（$e_\theta$）**。如果直接将远点位置按比例叠加到转向输出中，当直角弯进入视野上方时，控制器就会提前产生大转向角，导致小车在未到达弯道顶点前就提前内切转向。
- **解耦原则**：
  - **连续巡线层**：以近点横向误差为主控量（$P$），以近/中距离的航向变化作为阻尼项（$D$），严格限制远点对连续转向的直接权重。
  - **离散事件层**：远点视野**仅用于状态触发（检测到直角/锐角弯分支）**。在远点发现急弯后，小车应继续沿当前近线直行减速，直到拐点移动到近点判定区（或近线完全丢失）时，再触发定角度旋转或大曲率入弯。

### 当前代码存在的逻辑漏洞与隐患

**1. 远点航向误差直接进入线性 PD，诱发直角弯提前内切**

- 代码中 `observation->heading_error = line_error(near_center, width) - line_error(far_center, width)` 并在 `pd_steering` 中直接以 `-LINE_PID_KH * heading_error` 计入转向输出。  
- 当小车直行靠近 90° 直角弯时，弯道横向边在图像上方展开，导致 `far_center` 剧烈偏移，`heading_error` 瞬间激增。小车在未进入弯道前便被该前馈强行拽向一侧，脱离直道引导。  

**2. 逐行水平扫描机制在直角弯/锐角弯处极易“断流丢线”**

- `scan_segment` 采用**自底向上逐行水平扫描**（`y -= LINE_ROW_STEP`）。  
- 在直角弯与锐角弯拐点处，黑色赛道呈水平或倒 V 字走向：
  - 水平线段宽度剧增，触发 `LINE_MAX_SEGMENT_WIDTH_PERCENT`（55%）上限被滤除。  
  - 拐点处中心点横向跳变超出 `LINE_MAX_CENTER_JUMP_PERCENT`（18%）限制。  
- 扫描在此行直接 `break`，导致识别到的点数 `point_count < LINE_MIN_VALID_ROWS`（4 行），系统直接判定为非候选线，退化为 `LINE_STATE_LOST`，根本无法进入正确的 `LINE_STATE_CORNER`。  

**3. `branch_hint` 支路检测过于严苛且采样范围受限**

- `branch_hint()` 仅以提取到的最顶端点 `end` 为基准，在其两侧固定偏移处只探测 3 行（`LINE_BRANCH_ROWS`）。  
- 只要由于车速或采样间隔导致顶端点未能恰好落在分叉点附近，该检测就会漏判，无法将 `pending_turn` 锁定，导致小车进入直角/锐角弯时误判为直道丢线。  

**4. 锐角弯双线并存引发追踪歧义（跳线与震荡）**

- 锐角弯在摄像头视角下会同时出现“去程线”与“回程线”。
- 现有逻辑在无历史记录时默认取“离中心最近的连续黑段”；而在 `use_history` 下，窗口若因搜索宽度增大（如 `LINE_CORNER_WINDOW_MAX_PERCENT = 46%`），极易将回程线作为最近段吸附，使跟踪点在中途直接跳到对向赛道，导致小车在锐角顶点来回抽搐。  

**5. 转向限幅与舵向变化率（Slew Rate）响应滞后**

- `LINE_PID_SLEW_PER_FRAME = 2` 限制了每帧转向输出的增量。  
- 摄像头实际工作在 15 FPS 左右，从 0 爬升至 `LINE_PID_TURN_MAX`（10）需要 5 帧（约 330 ms）。对于锐角弯和突发直角弯，该响应速度无法提供足够的角加速度，导致车头未转过来就冲出 ROI。  

**6. 全局单一灰度阈值对反光与光照梯度极其脆弱**

- `calculate_binary_threshold` 在整个 ROI（纵向 30%~100%）内统计单一全局直方图。  
- 摄像头向下俯视时，上视野（远端）容易受场地环境光反射影响变亮，下视野（近端）偏暗。单一阈值会导致远端黑线被冲淡识别丢失，或近端地面被误判为黑线。

**7. 盲转缺乏绝对位姿或传感器闭环约束**

- 在 `LINE_STATE_CORNER` 下，代码完全依赖开环执行 `drive(LINE_FORWARD_CRAWL, -s_pending_turn * LINE_TURN_MAX)` 并在连续 3 帧重新看到线后退出。  
- 在三轮全向底盘上，电机受电池电压下降、地面摩擦力变化影响极大：
  - 电压足时容易在 3 帧确认期内快速过冲（Over-turn）；
  - 低速爬行（`LINE_FORWARD_CRAWL = 17`）在部分地面阻力下可能直接卡死不转，直到触发 3000 ms 超时被强制 `disarm_tracking`。  

### 改进与重构建议

- **双视野分工（近点纠偏，远点触发）**
  - 控制器横向误差仅取下方近端 $1\sim 2$ 个特征点（$y \in [70\%, 90\%]$）。
  - 远端区域（$y \in [30\%, 60\%]$）提取主线斜率变化与多分支特征；当检测到前方存在横向贯穿或大斜率突变时，仅做**弯道标志位置位**，严禁将其直接传入 PD 公式。
- **增加列扫描（Column-Scan）应对横向直角边**
  - 在行扫描遇到宽度超标或突变中断时，在断裂处启动局部垂直方向扫描（列扫描），确认是否存在水平延伸的直角/钝角边。
- **分级局部自适应二值化**
  - 将 ROI 纵向划分为近、中、远 3 个区块分别统计亮度直方图与阈值，消除俯视透视带来的光照梯度干扰。
- **动态解除 Slew Rate 限制**
  - 在状态机判定为 `CORNER` 或检测到大曲率时，临时放宽或跳过 `LINE_PID_SLEW_PER_FRAME`，允许电机以最大角速度快速回正。

# 1. 先回答你的核心问题：每一 tick 是不是只看近点？

**不应该只看最底部近点，但也绝不能让最远点直接决定转向。**

更合理的做法是：

> **近点用于即时纠偏，中距离预瞄点用于转向，远点只用于判断曲率、限速和提前准备。**

你现在代码里有一个明显风险：

```c
observation->lateral_error = line_error(near_center, width);

observation->heading_error =
    line_error(near_center, width) -
    line_error(far_center, width);
```

其中 `near_center` 是底部前 4 行，`far_center` 是顶部最后 4 行。  
然后 `pd_steering()` 里：

```c
target = (LINE_PID_KP * s_tracking_error -
          LINE_PID_KH * heading_error -
          LINE_PID_KD * delta_lateral_error) / LINE_PID_SCALE;
```

也就是说，**远处点的偏差会通过 `heading_error` 直接影响当前转向输出**。

这会带来你说的现象：

- 远端刚看到弯道；
- 小车实际还没到弯道入口；
- 控制器提前打方向；
- 小车提前偏离直线；
- 然后在近点又看到偏差反向修正；
- 造成画龙、过早转向、弯道入口切角失败。

所以正确策略不是“只看近点”，而是：

| 信息        | 作用                                               |
| ----------- | -------------------------------------------------- |
| 底部 1~8 行 | 当前是否压线、即时纠偏                             |
| 中部预瞄点  | 决定当前转向目标                                   |
| 远端点      | 判断前方弯度，用来减速、降置信度、准备进入弯道状态 |
| 远端点      | 不建议直接大权重参与转向                           |

尤其你的摄像头只有约 **15 FPS**，控制周期约 60~80 ms。  
如果远点权重太大，小车会“看到未来但身体没到”，非常容易过冲。

---

# 2. 当前代码整体能做什么，不能做什么？

当前代码已经有完整链路：

```text
UVC MJPEG
→ JPEG 解码 RGB565
→ ROI 亮度统计
→ 自适应阈值
→ 底部种子
→ 向上逐行找黑线段
→ points[]
→ lateral_error / heading_error
→ PD 控制
→ TB6612 电机
```

这套结构是合理的。

但现在更像是：

> “适合中等曲率黑线跟随”的实现。

对于你的目标：

- 直线稳定；
- 抗周围黑物干扰；
- 锐角弯；
- 直角弯；
- 出弯后继续沿线；

还有几个比较明显的漏洞。

---

# 3. 主要漏洞一覧

---

## 3.1 阈值系统：一旦对比度不足，直接变 0，容易丢线

`camera_display.c` 里：

```c
const int dark = histogram_percentile(..., CAMERA_BINARY_DARK_PERCENTILE);
const int light = histogram_percentile(..., CAMERA_BINARY_LIGHT_PERCENTILE);

if (light - dark < CAMERA_BINARY_MIN_CONTRAST) {
    return 0;
}
```

然后：

```c
static uint8_t filter_binary_threshold(uint8_t candidate)
{
    if (candidate == 0) {
        return 0;
    }
    ...
}
```

问题：

- 某一帧光线变化、反光、阴影、JPEG 压缩噪声；
- 导致 `light - dark < 32`；
- 阈值直接变 0；
- 巡线回调里：

```c
if (source_threshold == 0) {
    return false;
}
```

于是这一帧直接无候选线。

这会造成：

- 偶尔丢帧；
- 状态机进入 `LOST`；
- 电机突然减速；
- 在弯道前尤其危险。

### 建议

增加“阈值保持”机制。

例如：

```c
static uint8_t threshold_zero_frames = 0;

if (candidate == 0) {
    if (s_display.threshold_initialized && threshold_zero_frames < 5) {
        threshold_zero_frames++;
        return s_display.threshold_filtered;
    }
    return 0;
}

threshold_zero_frames = 0;
```

也就是：

> 短时对比度不足时，继续用上一帧阈值 3~8 帧，不要立刻丢失。

如果连续很多帧都没有对比度，再真正降为 0。

---

## 3.2 全局自适应阈值仍然容易被阴影、黑桌腿、黑胶带边缘干扰

当前阈值来自整个 ROI：

```c
x = 20%~80%
y = 30%~100%
```

这已经避开了左右边缘和顶部远处，但仍然有一个问题：

> 它只统计亮度，不判断这些暗色区域是不是“线”。

例如：

- 黑椅子脚；
- 地面阴影；
- 黑色电线；
- 反光里的暗斑；
- 黑胶带边缘反光；

都会影响直方图。

尤其是：

```c
#define CAMERA_BINARY_DARK_PERCENTILE 2
#define CAMERA_BINARY_LIGHT_PERCENTILE 90
#define CAMERA_BINARY_BLACK_FRACTION_PERCENT 20
```

如果画面中有少量很黑物体，`dark` 会被拉得很低；  
如果地面本身偏暗，`light` 也不高；  
最后阈值可能不适合真正的黑线。

### 建议

短期可先做三件事：

#### 1. 限制阈值范围更严格

现在：

```c
#define CAMERA_BINARY_THRESHOLD_MIN 25
#define CAMERA_BINARY_THRESHOLD_MAX 120
```

如果你的场地是白底黑线，可以把上限压低，例如：

```c
#define CAMERA_BINARY_THRESHOLD_MIN 25
#define CAMERA_BINARY_THRESHOLD_MAX 90
```

避免深灰色地面被识别成黑线。

#### 2. 增加黑线颜色约束

黑线通常不只是暗，还可能饱和度低。

RGB565 里可以近似计算：

```c
max_channel - min_channel
```

黑线特征：

```text
luma 低
max - min 小
```

可以考虑：

```c
dark = luma <= threshold && saturation <= SATURATION_MAX
```

例如：

```c
#define BLACK_SATURATION_MAX 60
```

这对彩色地面、阴影、彩色反光有一定抑制作用。

#### 3. 调试阶段允许固定阈值

先不要完全依赖自适应。  
你可以手动给一个阈值，例如 50、60、70，看小车能不能稳定。

如果固定阈值能跑，再让自适应阈值围绕这个值小范围变化。

---

## 3.3 当前找线只选“一个最合理黑段”，容易被干扰段骗

`scan_segment()` 的逻辑是：

- 每一行找连续黑色段；
- 选择宽度合理；
- 距离期望点最近；
- 的一个段。

这比随便找第一个黑段好很多，但仍然不够。

问题在于它没有充分利用：

- 上一帧线段位置；
- 上一帧斜率；
- 线段连续性；
- 线段角度；
- 黑段是否从底部种子连续延伸上来；
- 是否是孤立黑块。

所以可能出现：

```text
底部种子是真黑线
向上几行后遇到椅子脚
椅子脚距离期望点更近
宽度也满足
于是被当成线
```

或者：

```text
真线短暂变细
旁边黑物更宽
跟踪跳到黑物上
```

### 建议

把当前“逐行找最近段”升级为“带斜率预测的线段关联”。

核心思想：

```text
如果底部线在 x0，
并且上一帧或前几行显示线向右上方延伸，
那么下一行搜索中心不应该是上一行 x，
而应该是：

expected_x = last_x + slope * dy
```

其中 `slope` 可以用最近几个点估计：

```c
slope = (far_center - near_center) / row_distance
```

然后：

```c
expected_x = previous_x + slope * LINE_ROW_STEP;
```

这样有几个好处：

1. 弯道中搜索窗口更小；
2. 不容易跳到旁边孤立黑物；
3. 可以用更小的窗口，减少干扰；
4. 直角弯时更容易判断“线真的断了”，而不是乱找。

---

## 3.4 `LINE_SEARCH_HALF_PERCENT = 20` 对锐角弯可能太窄

当前：

```c
#define LINE_SEARCH_HALF_PERCENT 20
```

对于 240 宽图像：

```text
20% width = 48 px
```

也就是说 NORMAL 状态下，搜索窗口大约是：

```text
expected_x ± 48 px
```

这对缓弯可以。

但是锐角弯或直角弯时，黑线在图像中的位置可能一帧之间移动很多。  
尤其车体转向后，底部种子可能突然从中心跳到一侧。

结果：

```text
线其实还在
但已经出了搜索窗口
→ candidate = false
→ 进入 LOST
```

### 建议

不要简单无限扩大窗口，因为会引入干扰。  
更好的方式是：

#### 方案 A：NORMAL 窗口适度扩大

可以先试：

```c
#define LINE_SEARCH_HALF_PERCENT 24~30
```

例如：

```c
#define LINE_SEARCH_HALF_PERCENT 26
```

#### 方案 B：用斜率预测代替大窗口

如果加入斜率预测，窗口可以不必太大：

```c
half_window = base_half + abs(slope) * extra_factor;
```

弯道时斜率大，窗口自动变大；  
直线时斜率小，窗口自动变小。

这比固定 20% 更安全。

## 3.5 `LINE_MAX_CENTER_JUMP_PERCENT = 18` 也会让锐角弯断线

当前：

```c
#define LINE_MAX_CENTER_JUMP_PERCENT 18
```

对于 240 宽：

```text
18% = 43 px
```

如果相邻采样行中心跳变超过 43 px，就认为不连续：

```c
if (point_count > 0 && abs(segment.center - expected) > jump_limit) {
    break;
}
```

这对抑制干扰很有用，但对急弯不友好。

直角弯时，线在图像里可能突然横向位移很大。  
于是：

```text
真线被当成跳变
track_line 提前结束
valid_rows 不够
candidate = false
```

### 建议

可以分状态处理：

```c
NORMAL:   jump_limit 18%
CURVE:    jump_limit 25%
CORNER:   jump_limit 30%~35%
LOST:     允许更大，但必须配合方向限制
```

简单起步：

```c
#define LINE_MAX_CENTER_JUMP_PERCENT 22
```

如果加入斜率预测，则可以：

```c
jump_limit = base_jump + abs(slope) * row_step;
```

## 3.6 远端 `heading_error` 权重太大，确实会导致过早转向

你现在：

```c
#define LINE_PID_KP 12
#define LINE_PID_KH 8
#define LINE_PID_KD 4
```

`KH = 8` 不算小。  
而且 `heading_error` 是由底部 4 行和顶部 4 行直接相减得到：

```c
observation->heading_error =
    line_error(near_center, width) -
    line_error(far_center, width);
```

这意味着远端一点点偏斜，就会明显影响转向。

例如：

```text
近点还在线中间
远点看到右侧弯道
heading_error 变大
PD 立刻右转
但车还没到弯道入口
→ 提前切角
→ 偏出直线
```

这正是你担心的问题。

### 建议

#### 1. 降低 `heading_error` 权重

可以先试：

```c
#define LINE_PID_KH 3
```

或者：

```c
#define LINE_PID_KH 4
```

让近点误差主导。

#### 2. 对 `heading_error` 单独滤波

现在只对 `s_tracking_error` 做滤波：

```c
s_tracking_error = (old*3 + new*1)/4;
```

但 `heading_error` 没有滤波。

建议增加：

```c
static int s_filtered_heading = 0;

s_filtered_heading =
    (s_filtered_heading * 3 + heading_error) / 4;
```

然后只用滤波后的 `heading_error`。

#### 3. 限制 heading 对转向的最大贡献

例如：

```c
int heading_term = -LINE_PID_KH * heading_error / LINE_PID_SCALE;

if (heading_term > 4) heading_term = 4;
if (heading_term < -4) heading_term = -4;
```

也就是说：

> 远端可以提示，但不能抢方向盘。

#### 4. 远端只用于减速，不直接猛转

建议加入规则：

```c
if (abs(heading_error) > 40) {
    forward = LINE_FORWARD_SLOW;
}

if (abs(heading_error) > 60) {
    forward = LINE_FORWARD_CRAWL;
}
```

也就是：

> 看到前方有弯，先减速，不急着猛打方向。

---

## 3.7 当前速度策略太简单：只看横向误差，不看曲率

现在：

```c
static int forward_speed(int lateral_error)
{
    const int magnitude = abs(lateral_error);

    if (magnitude >= LINE_ERROR_LARGE) {
        return LINE_FORWARD_CRAWL;
    }
    if (magnitude >= LINE_ERROR_MEDIUM) {
        return LINE_FORWARD_SLOW;
    }
    if (magnitude > LINE_ERROR_DEADBAND) {
        return LINE_FORWARD_MEDIUM;
    }
    return LINE_FORWARD_FAST;
}
```

问题：

- 直线但前方急弯：横向误差还小，速度仍然快；
- 弯道入口：远端已经弯了，近端误差还小，速度仍然快；
- 置信度低时：速度不会下降；
- `valid_rows` 少时：速度不会下降；
- 阈值不稳定时：速度不会下降。

这会导致入弯速度过高。

### 建议

速度应该由多个因素决定：

```c
int forward = LINE_FORWARD_FAST;

// 横向误差
if (abs(lateral_error) > LINE_ERROR_MEDIUM) {
    forward = MIN(forward, LINE_FORWARD_SLOW);
}

// 远端弯度
if (abs(heading_error) > 35) {
    forward = MIN(forward, LINE_FORWARD_SLOW);
}

if (abs(heading_error) > 60) {
    forward = MIN(forward, LINE_FORWARD_CRAWL);
}

// 线段置信度
if (valid_rows < 6) {
    forward = MIN(forward, LINE_FORWARD_MEDIUM);
}

if (valid_rows < 4) {
    forward = MIN(forward, LINE_FORWARD_CRAWL);
}

// 阈值不稳定
if (threshold == 0 || threshold_unstable) {
    forward = MIN(forward, LINE_FORWARD_CRAWL);
}
```

核心思想：

> 只要前方有弯、线短、置信度低，就先减速。

---

## 3.8 `LINE_ERROR_DEADBAND = 18` 太大，直线容易画龙

当前：

```c
#define LINE_ERROR_DEADBAND 18
```

误差计算是百分比：

```c
error = (width/2 - center) * 100 / (width/2)
```

对于 240 宽，半宽 120 px。

```text
error = 18
约等于 21.6 px
```

也就是说：

> 线偏出中心 20 多个像素内，PD 不修正。

这太大了。

小车可能会：

```text
慢慢偏到右边
到误差超过 18 才开始修
修多了又偏到左边
再等误差超过 18 再修
```

形成低频画龙。

### 建议

先降低死区：

```c
#define LINE_ERROR_DEADBAND 6
```

或者：

```c
#define LINE_ERROR_DEADBAND 8
```

如果抖动，再稍微增加。  
但 18 对巡线来说偏大。

---

## 3.9 `LINE_MIN_VALID_ROWS = 4` 对干扰场景偏少

当前：

```c
#define LINE_MIN_VALID_ROWS 4
```

每 4 行扫一次，4 行只覆盖约 16 像素高度。

在 160 高图像里，这个信息量不大。  
如果刚好有 4 个连续黑点/黑块，就可能被认为是一条线。

### 建议

正常跟随可以提高到：

```c
#define LINE_MIN_VALID_ROWS 5
```

或：

```c
#define LINE_MIN_VALID_ROWS 6
```

但在 `LOST` 重捕获和 `CORNER` 出弯时，可以临时允许 3~4 行，避免太严格导致无法恢复。

也就是分状态：

```text
NORMAL arm:   5~6 rows
LOST reacquire: 3~4 rows
CORNER exit:  3~4 rows
```

## 3.10 `pending_turn` 一旦设置，不会自动过期，这是一个明显状态机漏洞

当前 `update_turn_memory()`：

```c
if (observation == NULL || !observation->candidate ||
    observation->branch_direction == 0 || s_pending_turn != 0 ||
    s_state != LINE_STATE_NORMAL) {
    if (s_pending_turn == 0) {
        s_hint_direction = 0;
        s_hint_frames = 0;
    }
    return;
}
```

一旦：

```c
s_pending_turn = direction;
```

之后如果 `s_pending_turn != 0`，这个函数基本不会再更新它。

也就是说：

```text
之前某帧误识别到右侧支路
pending_turn = +1
但小车继续走直线
之后一直没有旧线消失
pending_turn 一直保留
```

再之后如果因为噪声短暂丢线：

```text
状态机可能带着旧的 pending_turn 进入 CORNER
然后按错误方向转弯
```

这是很危险的。

### 建议

给 `pending_turn` 加寿命和失效条件。

例如：

```c
static uint8_t s_pending_age_frames = 0;
static uint8_t s_pending_no_branch_frames = 0;
```

规则：

1. 每帧 `pending_turn != 0` 时：

```c
s_pending_age_frames++;
```

2. 如果超过 1.5~2 秒还没进入 CORNER，清除：

```c
if (s_pending_age_frames > 25) {
    clear_turn_plan();
}
```

按 15 FPS 算，25 帧约 1.6 秒。

3. 如果旧线仍然稳定可见，但支路提示连续消失，也应该清除：

```c
if (candidate && observation.old_line_visible &&
    observation.branch_direction == 0) {
    s_pending_no_branch_frames++;
} else {
    s_pending_no_branch_frames = 0;
}

if (s_pending_no_branch_frames > 6) {
    clear_turn_plan();
}
```

否则一个历史误识别会影响后面很久。

## 3.11 直角弯不一定有“支路”，当前代码可能进不了 CORNER，而是进 LOST

你现在的弯道逻辑主要来自：

```c
branch_hint()
```

它检测的是：

```text
主线旁边是否有一条分支线
```

但是很多直角弯不是分支，而是：

```text
线到这里直接 90° 折走
```

这种情况下可能没有 `branch_direction`。

当前状态机：

```text
NORMAL
→ candidate=false
→ LOST
```

而不是：

```text
NORMAL
→ 直角弯搜索
```

于是小车可能：

```text
直线爬行
等待最后种子附近重捕获
但新线在侧面
重捕获窗口不允许
最后停车
```

这是过直角弯的大问题。

### 建议

增加一种“线尾弯道”判断。

当出现以下情况时，不要只进入 `LOST`，而应该进入 `CORNER_SEARCH`：

1. 上一帧线还稳定；
2. `valid_rows` 突然下降；
3. 顶部点消失；
4. 底部种子靠近图像左/右边缘；
5. 最近几帧 `heading_error` 已经明显偏左或偏右；
6. 或者最后几帧点斜率很大。

可以定义：

```c
bool line_end_corner =
    last_valid_rows >= 6 &&
    observation.valid_rows < 3 &&
    abs(last_heading_error) > 40;
```

如果成立：

```c
s_pending_turn = direction_of(last_heading_error);
enter_corner_search();
```

这样直角弯也有机会进入转向搜索，而不是被动 `LOST`。

---

## 3.12 当前 CORNER 预测太理想化，假设小车按固定角速度转

现在：

```c
#define LINE_CORNER_PREDICT_STEP_PERCENT 4
```

然后：

```c
predicted = s_corner_origin_x +
            s_pending_turn * step * s_corner_frames;
```

这等于假设：

> 每帧新线位置按固定百分比移动。

但实际受很多因素影响：

- 电机转速；
- 电池电压；
- 地面摩擦；
- 转向机构角度；
- 车轮打滑；
- 车身姿态；
- 摄像头安装角；
- 弯道角度；
- 车架几何。

所以预测很容易偏。

### 建议

CORNER 状态下不要太依赖精确预测点。  
应该变成“大窗口搜索 + 稳定确认”。

例如：

```text
CORNER 搜索时：
1. 允许搜索窗口更大；
2. 优先搜索 pending_turn 方向；
3. 只要底部连续 3~5 行出现合理新线；
4. 并且新线靠近图像中心或预测方向；
5. 就退出 CORNER；
```

不要要求新种子非常接近固定预测点。

否则：

```text
预测点偏左
真实新线偏右
明明已经看到新线
但被 corridor 拒绝
继续盲目转弯
```

---

## 3.13 `LOST` 重捕获太保守，可能拒绝真实新线

当前 `LOST` 里：

```c
const int confirm_window = positive_percent((int)width,
                                            LINE_SEARCH_HALF_PERCENT,
                                            LINE_SEARCH_HALF_MIN);

const bool near_last_seed =
    abs(observation.seed_x - s_seed_x) <= confirm_window;
```

`confirm_window` 约 20% 宽度。

这个设计目的很好：

> 防止把远处椅子脚当成重捕获线。

但副作用是：

> 如果小车已经转向，真实新线已经移动到旧种子旁边较远位置，会被拒绝。

尤其在直角弯：

```text
旧线在中间
转弯后新线在右侧 80 px
confirm_window 只有 48 px
→ 不允许恢复
```

### 建议

`LOST` 不应该只有一个固定 `confirm_window`。

可以分情况：

#### 情况 1：直线丢失

保持严格：

```text
必须在旧种子附近
```

#### 情况 2：有转向意图 / 刚进入弯道

允许新种子向转向方向偏移：

```c
if (s_pending_turn != 0 || s_state == LINE_STATE_CORNER) {
    allow_shift = larger_window;
} else {
    allow_shift = normal_window;
}
```

例如：

```text
普通丢失：±20% width
弯道丢失：±35% width，且只允许朝转向方向偏移
```

这样既能防椅子脚，又不会拒绝真实弯道新线。

## 3.14 `finish_candidate` 很容易被宽黑物误触发

当前：

```c

```

注意这个宽度是相对于局部搜索窗口，不是整幅图像：

```c
const int window_width = right - left + 1;

```

如果局部窗口只有 80 px 宽：

```text
62% = 50 px
```

一个黑色桌腿、阴影、胶带团、终点附近黑块，只要连续几行够宽，就可能触发终点停车。

而且：

```c

#define LINE_FINISH_CONFIRM_FRAMES 5U
```

在 15 FPS 下，5 帧只有约 300 ms。  
如果误识别稳定，很容易误停。

### 建议

如果你的目标不是“识别终点横线”，建议暂时禁用 finish：

```c
#define LINE_FINISH_WIDTH_PERCENT 90
#define LINE_FINISH_MIN_ROWS 4
#define LINE_FINISH_CONFIRM_FRAMES 8
```

或者直接在状态机里注释：

```c
#if 0
if (observation.finish_candidate && candidate) {
    ...
}
#endif
```

如果确实要检测终点横线，应该要求：

1. 宽度接近整个 ROI；
2. 多行连续；
3. 横向几乎水平；
4. 不是斜黑块；
5. 前后几帧都有；
6. 最好结合赛道流程，不在起跑阶段启用。

## 3.15 `branch_hint()` 对干扰物也可能误报

`branch_hint()` 会在顶部点两侧偏移搜索：

```c
end->x + direction * offset
```

然后连续几行有黑段就认为有支路：

```c
if (hits >= 2) {
    found_direction = direction;
}
```

问题：

- 黑椅子脚；
- 黑胶带残留；
- 阴影；
- 另一条旧赛道；
- 黑色边框；

都可能被当成支路。

一旦 `pending_turn` 被设置，再加上 3.10 的不过期问题，风险更大。

### 建议

增加支路确认条件：

1. 支路必须从主线侧向连续分叉；
2. 支路宽度应与主线接近；
3. 支路中心与主线距离应随行数增加；
4. 不能只是孤立 2 行；
5. 支路提示必须和当前远端斜率方向一致；
6. 如果旧线仍然很直，不应轻易进入转弯。

例如：

```c
if (branch_direction != 0) {
    if (sign(branch_direction) != sign(heading_error)) {
        branch_direction = 0;
    }
}
```

也就是说：

> 如果远端斜率没有显示那个方向有弯，就不要相信分支。

# 5. 针对“锐角弯、直角弯”的具体建议

你现在的弯道逻辑需要补三层。

---

## 5.1 第一层：弯道前减速

当远端出现大 `heading_error`：

```c
if (abs(heading_error) > 35) {
    forward = min(forward, LINE_FORWARD_SLOW);
}

if (abs(heading_error) > 55) {
    forward = min(forward, LINE_FORWARD_CRAWL);
}
```

不要等近端偏了才减速。

---

## 5.2 第二层：进入弯道后缩短预瞄

现在你是从底部向上扫，然后用最远几行参与控制。  
建议在弯道里降低预瞄距离。

可以定义一个 `lookahead_rows`：

```c
int lookahead_rows;

if (state == NORMAL && abs(heading_error) < 20) {
    lookahead_rows = 10;
} else if (abs(heading_error) < 50) {
    lookahead_rows = 6;
} else {
    lookahead_rows = 3;
}
```

然后控制误差不再用最顶部 `far_center`，而是用预瞄点：

```c
int x_look = get_point_at_rows(points, point_count, lookahead_rows);
int lateral_error = line_error(x_look, width);
```

也就是说：

> 直线看远一点；  
> 弯道看近一点；  
> 急弯只看入口附近。

这能有效减少过早转向。

---

## 5.3 第三层：直角弯用 CORNER_SEARCH，不要依赖普通巡线

直角弯时，线可能突然不在前方。  
此时继续用普通 PD 会失败。

建议新增一个状态：

```c
LINE_STATE_TURN_SEARCH
```

进入条件：

```text
刚还有稳定线
现在 valid_rows 突然不足
最近斜率或支路提示了方向
```

行为：

```text
1. forward 降到 0 或很低；
2. turn 用最大允许方向；
3. 每帧全 ROI 底部扫描；
4. 发现新底部种子连续 3 帧；
5. 切回 NORMAL；
```

伪代码：

```c
if (state == LINE_STATE_TURN_SEARCH) {
    line_observation_t obs;

    // 弯道搜索时放宽限制，但不要全局乱找
    bool found = track_line(
        frame, width, height, threshold,
        false,       // 不完全依赖旧 history
        width / 2,
        -1,          // 不用 corridor
        width / 2,
        draw_overlay,
        &obs
    );

    if (found &&
        obs.valid_rows >= 3 &&
        abs(obs.seed_x - width / 2) < width / 4) {

        if (++corner_exit_frames >= 3) {
            state = LINE_STATE_NORMAL;
            update_seed(&obs);
            reset_pd();
            drive(LINE_FORWARD_CRAWL, 0);
        }
    } else {
        corner_exit_frames = 0;

        // 三轮小车如果支持原地转向，forward 给 0
        drive(0, turn_direction * LINE_TURN_MAX);

        // 如果转太久没线，可以反扫一次
        if (esp_timer_get_time() - search_start_us > 800000) {
            turn_direction = -turn_direction;
            search_start_us = esp_timer_get_time();
        }
    }

    return;
}
```

注意：是否 `forward = 0` 取决于你的三轮结构。

如果你的小车是：

- 两个驱动轮 + 万向轮；

可以原地转向。

如果是：

- 前轮转向 + 后轮驱动；

则原地转向能力有限，应该用：

```c
drive(LINE_FORWARD_CRAWL / 2, turn_max)
```

而不是完全 0。

# 6. 关于“看太远会过早转向”的具体控制策略

建议把控制改成下面的结构：

```text
1. 底部种子：判断车还在线上
2. 近区 0~10 行：计算当前横向误差
3. 预瞄点 10~20 行：决定转向目标
4. 远区 20 行以上：只计算曲率，用于减速
5. 曲率大：缩短预瞄、降低速度
6. 线断了：进入弯道搜索，而不是继续用远点猜
```

不要这样做：

```text
远端偏右 → 立刻大右转
远端偏左 → 立刻大左转
```

而应该这样做：

```text
远端偏右 → 降低速度
预瞄点偏右 → 小幅右转
近端已经偏右 → 正式修正
线突然结束 → 进入角点搜索
```

# 7. 建议加入“预瞄点控制”，不要直接用 far_center

你现在 `near_center` 和 `far_center` 都是 4 行平均：

```c
const int near_count = point_count < 4 ? point_count : 4;
const int far_count = point_count < 4 ? point_count : 4;

const int near_center = average_points(points, 0, near_count);
const int far_center = average_points(points, point_count - far_count, far_count);
```

这个远端点太远了。  
尤其 `point_count` 可能二十多行，远端接近图像顶部。

建议改成：

```c
// 只用底部附近一段做控制
int control_count = point_count < 6 ? point_count : 6;
int x_control = average_points(points, 0, control_count);

// 用中段做曲率判断
int mid_count = point_count < 12 ? point_count : 12;
int x_mid = average_points(points, point_count / 2, ...);

// 最远点只用于曲率
int x_far = average_points(points, point_count - far_count, far_count);
```

然后：

```c
lateral_error = line_error(x_control, width);

heading_error = line_error(x_control, width) -
                line_error(x_mid, width);
```

不要让最顶部 4 行直接决定转向。

```c

y = 30%~100%
```

弯道阶段：

```c
#define LINE_ROI_LEFT_PERCENT 15
#define LINE_ROI_RIGHT_PERCENT 85
```

不要一次性用太大范围。

## 11.3 时间层

任何黑段必须满足连续多帧才允许影响控制。

建议：

- 底部种子连续 2~3 帧；
- 支路连续 3~4 帧；
- 终点线连续 5~8 帧；
- 丢线必须连续 2~3 帧确认；
- 重捕获必须连续 2 帧靠近旧种子。

你当前已经有部分确认，但可以更严格。

## 11.4 几何层

真正的黑线应该满足：

1. 底部种子存在；
2. 向上连续；
3. 相邻行中心变化连续；
4. 宽度不会突然暴涨；
5. 斜率不会瞬间乱跳；
6. 不会孤立出现在远处；
7. 不会和底部种子断开。

可以加一个简单连续性评分：

```c
int score = 0;

if (valid_rows >= 5) score += 20;
if (segment_width_ok) score += 20;
if (center_jump_small) score += 20;
if (slope_consistent) score += 20;
if (near_bottom_seed) score += 20;
```

低于分数就降低置信度或拒绝。

# 12. 推荐的状态机改法

你当前是：

```text
NORMAL
CORNER
LOST
```

建议扩展为：

```text
NORMAL
CURVE_SLOW
TURN_SEARCH
LOST
FINISH
```

或者简单一点：

```text
NORMAL
CORNER
LOST
```

但把 `CORNER` 分成两种：

```text
BRANCH_CORNER：有支路提示
LINE_END_CORNER：线尾突然消失
```

---

## NORMAL

负责：

- 直线；
- 缓弯；
- 小曲率跟随；
- 预瞄点控制；
- 远端只限速。

---

## CURVE_SLOW

可以不是独立状态，而是 NORMAL 里的降速模式：

```c
if (abs(heading_error) > 35 || valid_rows < 6) {
    speed = SLOW;
}
```

---

## CORNER / TURN_SEARCH

负责：

- 直角弯；
- 锐角弯；
- 线断了但知道大概方向；
- 原地或低速转向；
- 全底部窗口搜索新线；
- 找到新线后回 NORMAL。

---

## LOST

负责：

- 不知道方向的丢失；
- 短时间保持；
- 慢速左右小幅度搜索；
- 超时停车。

---

# 13. 一个更合理的每帧处理流程

建议最终流程类似：

```text
1. 解码得到 240×160 RGB565
2. 计算阈值，如果对比度短暂不足，保持上一帧阈值
3. 底部多行扫描，找种子
4. 从底部种子向上扫描，结合上一帧斜率预测
5. 得到 points[]
6. 判断线段置信度：
   - valid_rows
   - 宽度稳定
   - 跳变小
   - 斜率连续
7. 计算近点误差
8. 计算预瞄点误差
9. 计算远端曲率
10. 根据曲率选择预瞄距离和最大速度
11. 如果线连续：
    NORMAL PD
12. 如果线短但曲率大：
    进入弯道搜索
13. 如果线完全丢失：
    根据最后方向进入 CORNER_SEARCH 或 LOST
14. 出弯后连续 3 帧看到稳定底部种子，再回 NORMAL
```

# 14. 针对你当前代码，最优先改的 8 件事

## 第一优先级：先让它稳

### 1. 阈值保持

### 2. 降低 `LINE_ERROR_DEADBAND`

### 3. 降低 `LINE_PID_KH`

# 15. 最终建议：你现在的控制思路应该这样改

可以总结成一句话：

> **当前帧的转向，主要由近点和中距离预瞄点决定；远点只用来判断前方是否有弯并提前减速；一旦线断了，就切换到角点搜索状态，而不是继续用远点猜测。**

也就是说：

```text
直线：
    近点误差 + 小权重远端斜率

缓弯：
    缩短预瞄，降低速度，近点主导

锐角/直角弯：
    检测到线尾/大曲率后进入 TURN_SEARCH
    低速或原地转向
    找到新底部种子后恢复跟随

丢线：
    直线丢失 → 小范围重捕获
    弯道丢失 → 按转向方向放宽搜索
    长时间丢失 → 停车
```

# 16. 简版结论

你现在的代码不是完全不能用，而是有几个关键漏洞：

1. **远点 `heading_error` 权重太大，会过早转向。**
2. **速度只看横向误差，不看曲率，容易入弯过快。**
3. **`pending_turn` 不会过期，误识别支路会造成错误转弯。**
4. **直角弯没有支路时会进 `LOST`，而不是主动转弯搜索。**
5. **`LOST` 重捕获窗口太保守，可能拒绝真实新线。**
6. **自适应阈值一旦对比度不足直接为 0，容易瞬时丢线。**
7. **`LINE_ERROR_DEADBAND = 18` 太大，直线容易画龙。**
8. **`finish_candidate` 容易被宽黑物误触发。**
9. **搜索窗口和跳变限制对锐角弯偏严格。**
10. **电机方向、转向符号和三轮混控必须实车验证。**

最合理的方向是：

> 近点控车，中点预瞄，远点限速；  
> 弯道提前减速；  
> 直角弯用专门的角点搜索，而不是硬用普通巡线。
