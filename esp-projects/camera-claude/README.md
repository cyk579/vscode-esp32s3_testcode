# camera-claude

另一组能跑的摄像头巡线 / 避障 / 推球代码，移植到本车（引脚重映射 + 三处适配）。

原仓库是 `esp-projects/camera-other_group`，一个字没动。控制逻辑、视觉算法、
参数全部保留他们的原值 —— 目的是先在本车上复现他们的效果，而不是改进它。
本车之前那套重构（两个比例项 + host 回归测试）已经从这个目录里删掉了。

底盘同型号，接线不同，所以移植的工作量集中在引脚。改动都在注释里标了原值。

## 当前状态：启动就崩，正在排查

`3ed8ddc` 在本车上实测**启动崩溃循环**：屏幕约每 500ms 闪一次并重画，车不动。

500ms 正好是 `app_main()` 开头那个 `vTaskDelay(pdMS_TO_TICKS(500))`，也就是
每次复位都跑一遍 `tft_init` + 清屏 + 画字，然后崩，再复位。屏幕**有显示**说明
`tft_init` 过了（它里面的 `ESP_ERROR_CHECK` 失败会直接 abort），所以崩点在它之后。

已排除的：

- 不是编码器 —— `3ed8ddc` 那版 `USE_ENCODER` 是关的
- 不是 TFT 引脚 —— 和 camera-test（本车已验证能跑）的五个脚完全一致，CS=47 是实测过的
- 不是 LEDC 撞车 —— 电机 TIMER_0 / 通道 0-1-2，舵机 TIMER_1 / 通道 3-4，不重叠，
  而且两边都没包 `ESP_ERROR_CHECK`，失败也不会崩
- 不是字库越界 —— `ascii_font8x16[95][16]` 定死大小，`tft_draw_char` 有
  `c < 32 || c > 126` 边界检查，未定义的字只是画成空白
- 不是 NVS 没初始化 —— `wifi_mjpeg.c` 里有 `nvs_flash_init()` 和 erase 重试
- 不是板级配置 —— 逐键对过 camera-test 已验证的 `sdkconfig`，Flash/PSRAM/主频全一致

**所以静态分析到此为止，需要串口日志。** 为此加了 `TEST_MODE 8`，而且设成了默认值。

它的初始化顺序和模式 6 **完全一致**（包括 `display_task` 在摄像头之前起，
优先级 4 会抢占 `app_main`），区别只有三点：每步之前打一行 `[n/9]`、
每步之间停 300ms、全程不驱动电机。串口里**最后出现的那个 `[n/9]` 就是崩溃点**。

```
[1/9] TFT      [4/9] 编码器 PCNT      [7/9] 舵机（电流冲击最大）
[2/9] 电机     [5/9] 屏幕刷新任务      [8/9] 摄像头取流（USB 枚举）
[3/9] PID      [6/9] 超声波任务        [9/9] Wi-Fi + MJPEG
```

九步全过的话会进心跳循环，每 2 秒打一次距离、三个编码器计数、剩余内存 ——
那就说明崩在巡线主循环而不是初始化。**手拨轮子看计数变不变，这是验编码器接线
最快的办法。** 排查完把 `main.c` 第 17 行附近的 `TEST_MODE` 改回 `6`。

看日志必须用 **UART 口**（GPIO43/44 那个，走板载 USB-UART 桥）。原生 USB 口是
USB-Serial-JTAG，GPIO19/20 被摄像头抢去做 USB host 了，摄像头一初始化就没输出。

## 先回答三个问题

**要不要拉代码？** 不用，代码已经在这个目录里了。

**能直接烧录吗？** 能。当前默认是排查模式，不驱动电机，比模式 6 安全。
但**还是把车垫起来** —— 万一你改回了 6。原因见下面「烧录前必看」。

**要改什么？** 编译前不用改。烧上去之后大概率要改两个值：摄像头俯仰角的正负
（`SERVO_INIT_PITCH_DEG`）和屏幕方向（`TFT_MADCTL_VALUE`），改哪个看现象。

## 引脚对照

`main/board_pins.h` 是唯一的引脚定义处，每一行都标了他们的原值。

| 外设 | 本车 | 他们 |
| --- | --- | --- |
| A 轮 PWM / IN1 / IN2 | 9 / 12 / 10 | 4 / 6 / 5 |
| B 轮 PWM / IN1 / IN2 | 4 / 6 / 5 | 9 / 11 / 10 |
| D 轮 PWM / IN1 / IN2 | 16 / 7 / 15 | 40 / 42 / 41 |
| TB6612 STBY | 8 | 无（跳线到 VCC） |
| 超声波 TRIG / ECHO | 18 / 11 | 3 / 14 |
| 舵机 水平 / 俯仰 | 1 / 2 | 8 / 18 |
| TFT MOSI/CLK/CS/DC/RST | 14/13/47/21/38 | 21/47/48/17/16 |
| A 轮编码器 A/B 相 | 39 / 40 | 7 / 15 |
| B 轮编码器 A/B 相 | 17 / 3 | 12 / 13 |
| D 轮编码器 A/B 相 | 41 / 42 | 2 / 1 |
| USB 摄像头 D-/D+ | 19 / 20 | 同（硬件固定） |

三个坑，抄脚号会中：

**A/B/D 是按几何角色映射的，不是按脚号。** A、D 是两个斜置驱动轮，B 是横移轮。
他们的 A 脚号（4/6/5）恰好等于本车的 B 脚号 —— 照抄脚号会把驱动轮和横移轮接反，
车会往奇怪的方向走，而且日志完全正常。

**他们的舵机脚 8 是本车的 TB6612 STBY。** 照抄的话舵机的 50Hz PWM 会去砍电机使能。

**编码器那六个脚没有余量，别挪。** 模组只引出 33 个 GPIO（0~21、38~48，没有 26，
也没有 33~37 —— 那几个在模组内部给 OPI Flash 和 OCT PSRAM 用了）。21 个已被占用，
剩 12 个里真正能用的正好 6 个：3、17、39、40、41、42。其余每个都有理由排除：

- 43 / 44 是 UART0，占了就没法 monitor 和烧录
- 45 / 46 数据手册表 4-1 写明弱下拉、上电必须为低，45 还决定 VDD_SPI 电压
- 0 是 BOOT 脚，弱上拉
- **47 / 48 是 1.8V 域** —— 表 3-1 脚注 2：R8V/R16V 的 VDD_SPI 已设为 1.8V，
  本车模组是 N32R16V。编码器输出 3.3V 逻辑，灌进去超规格，有损坏风险

41 / 42 原来是四路红外的 OUT1/OUT2，红外已从车上拆除才腾出来的。所以 `track.c`
里加了一句 `#error`：一旦有人把 `track_config.h` 切回红外模式，`track_init()`
会把这四个脚重配成输入，同时打死 D 轮编码器和两个舵机 —— 症状是"车能跑但转向
不对、摄像头不动"，极难追到引脚。现在它会直接编译失败。

## 烧录

```bash
cd esp-projects/camera-claude
idf.py set-target esp32s3
```

`set-target` 这次必须执行 —— 我删了旧的 `sdkconfig`（里面还留着已删项目的配置
键），它会从 `sdkconfig.defaults` 和 `sdkconfig.defaults.esp32s3` 重新生成。
八线 Flash / OPI / 32MB / 八线 PSRAM 这些板子关键项都在后者里。

```bash
idf.py build
```

第一次 build 会去下载 `espressif/usb_stream` 和 `espressif/esp_new_jpeg`
两个组件（他们用的 USB 摄像头栈，和本车原来的 `usb_host_uvc` + `esp_jpeg`
不是一套，不能混用）。要联网。

```bash
idf.py -p COM5 flash monitor
```

COM 口在设备管理器里确认。退出 monitor 是 `Ctrl+]`。

**必须插 UART 口，不是原生 USB 口。** 板子上两个 USB 口的日志通路不一样：

| 口 | 通路 | 摄像头初始化后 |
| --- | --- | --- |
| UART 口 | UART0，GPIO43/44，走板载 USB-UART 桥 | 一直有日志 |
| 原生 USB 口 | USB-Serial-JTAG，GPIO19/20 | **没输出** |

GPIO19/20 是 USB D-/D+，被摄像头抢去做 USB host 了。插原生口的话，你会看到
前面几行启动日志然后突然断掉 —— 那不是崩溃，是通路被占了。查启动崩溃必须用
UART 口，否则你看到的"最后一行"是假的。

VS Code 的 Espressif IDF 扩展也行：底栏选 esp32s3 和串口，点火焰图标
「Build, Flash and Monitor」。

**我没能在本机验证编译** —— 这台机器没有 `idf.py`，这些文件又需要 ESP-IDF
头文件，没法像纯 C 那样在 PC 上编。第一次 build 就是在你机器上。报错贴给我。

## 烧录前必看

**车垫起来，别落地。** 上电 500ms 后电机就会动，而且是无条件动：

`camera_line_lost` 初值是 0，`pid_update()` 看到「没丢线」就直接进巡线分支，
误差初值也是 0，于是两个驱动轮同时输出 1385 counts（17% 占空比）往前冲。
要等摄像头连续 3 帧看不到线（约 120ms）才会切到「原地转找线」。

也就是说**它开机就往前跑，不管前面有没有线**。他们的车是摆在线上开机的，所以
这个行为对他们没影响。本车原固件有「连续 3 帧看到线 + 600ms」的起步门控，
他们这套没有。垫起来看轮子转向对不对，再落地。

**摄像头断流不会停车。** 他们没做断流保护。USB 摄像头掉了的话，误差和丢线标志
都冻在最后一帧的值上，如果冻在「没丢线、误差 0」，车会一直直行。本车原固件有
1200ms 断流断电。急停靠电源开关，别靠拔 USB。

## 上电后先确认摄像头朝哪

巡线要俯视地面。初始俯仰角写的是 `+30°`（`camera_track.c` 的
`SERVO_INIT_PITCH_DEG`），正负取决于舵机怎么装的，他们的车是往下，本车未知。

看画面最快的办法是连 Wi-Fi：SSID `ESP32_CAM`，密码 `12345678`，
浏览器开 `http://192.168.4.1:8080`。**看到天花板就把这个值改成 `-30.0f`。**

顺便说一句：这个热点是明文弱口令，MJPEG 流没有任何认证，同一个 AP 下谁都能看。
调试很方便，比赛现场注意。不需要预览的时候把 `main.c` 里的
`wifi_mjpeg_start(frame_q)` 注释掉。

## 屏幕会显示什么

下面描述的是 `TEST_MODE 6`（完整流水线）。当前默认是 8（排查模式），
屏幕上只有清屏后 `display_task` 刷的那几行，没有标题。

模式 6 开机画一行标题，然后 `display_task` 每 100ms 刷四行：

```
FULL PIPELINE MODE     ← 黄色，只画一次
Dist: 12.3 cm          ← 白色，超声波
SpdA: 0                ← 绿色
SpdB: 0                ← 绿色
SpdD: 0                ← 绿色
```

实际看到的比这个难认，两个原因，都不是屏幕坏了：

**字模只填了 19 个字符。** `tft.c` 的字库里作者自己写了「此处省略大量字体数据」，
实际只有 `空格 ! . : 0-9 A B D E S c m`，其余字符全是空白。所以：

- `FULL PIPELINE MODE` → 几乎整行空白，只在 E、D、E 的位置有三个字母。
  而且这行 18 个字符超过了 `tft_draw_string` 的换行点（x > 120，即 16 个字符），
  后两个字符会折到第二行，压在 y=16 附近。
- `Dist: 12.3 cm` → `D   : 12.3 cm`（i、s、t 没有字模）
- `SpdA: 0` → `S  A: 0`（p、d 没有）

数字和小数点是全的，所以**距离读数是可信的**，那是这块屏唯一有用的信息。

**`SpdB` 会恒为 0，但 A 和 D 不会。** 编码器现在接上了（39/40、17/3、41/42），
三行读的是真实计数。B 那行恒为 0 是另一个原因：`pid.c` 里巡线分支两处都写着
`int motor_B_power = 0;`，横移轮在巡线时本来就不给功率，只在避障横移和原地转
的时候由 `pid_manual_control` 开环驱动。所以 `SpdB: 0` 是对的，不是接线问题。

屏幕上没有巡线误差、没有当前阶段、没有摄像头画面。这些只在串口里，而且
`TEST_MODE 6` 只在事件发生时打印（检测到障碍物、避障完成、球已居中……），
**没有周期性的状态行**。

## 调巡线用 TEST_MODE 3，不要用 6

`main.c` 第 17 行。模式 3 是「巡线 + 避障」，没有推球，而且每 100ms 打一行：

```
态:0 距:12.3cm | 传:0 0 0 0 | 误:-0.42 | A:1385 B:0 D:1385
```

- `态` 避障状态机：0=巡线 1=左移 2=前进 3=右移 4=停
- `误` 巡线误差，范围 ±3，负=线偏左
- `A/B/D` 三个轮的实际输出 counts（满量程 8191，本车上限 3604）
- `传` 是红外传感器，摄像头模式下恒为 0

**判断巡线好不好看这行的 `误`，不要看屏幕。** 模式 6 没有这行，调参时抓瞎。

两个模式的避障触发距离还不一样：模式 3 是 5cm，模式 6 是 8cm。

调好了再把 `TEST_MODE` 改回 6 跑完整流程。

## 屏幕方向不对怎么调

他们的屏和本车的屏同型号 ST7735，但面板变体不同。他们是竖屏 `0xC8` + 行列偏移
`(2,1)`，本车原固件实测是横屏 `0xA0` + 偏移 `(0,0)`。

我保留了他们的值。因为他们整套文字坐标（y=0/30/60/80/100、x 超过 120 换行）
是按 128 宽竖屏排的，改成横屏文字会跑出屏幕。方向或位置不对，改 `tft.c` 顶部：

```c
#define TFT_MADCTL_VALUE 0xC8   /* 本车原固件是 0xA0 横屏 */
#define TFT_COL_OFFSET 2        /* 本车原固件是 0 */
#define TFT_ROW_OFFSET 1        /* 本车原固件是 0 */
```

## 除引脚以外改了什么

四处，都在原地注释里标了原值。

**1. `motor.c` 补了 STBY 拉高。** 他们的板子 STBY 跳到 VCC，代码里没这一脚。
本车 STBY 接在 GPIO8，不拉高三个轮子全不转，而且日志一切正常。

**2. `encoder.c` 整个包进 `#ifdef USE_ENCODER`，现在是开的（`USE_ENCODER 1`）。**
六个脚重新分配过：他们的编码器脚在本车上是 D 轮方向 ×2、A 轮方向、TFT 时钟、
两个舵机，PCNT 把这些配成输入会和输出直接顶牛，所以不能照抄。现用 39/40（A）、
17/3（B）、41/42（D），理由见上面第三个坑。任务栈从 1024 提到 2048 —— 里面有
浮点运算和 PCNT 调用，1024 太紧。

关掉这个开关比开着更安全，但**接了编码器却不开**只是丢掉闭环；
**没接却开着**才是真的坏：PCNT 恒读 0，闭环每周期补 +500 一路顶到
`PID_MAX_SPEED`，车会以 44% 占空比冲出去，而不是巡航的 17%。

**3. `pid.c` 的 `speed_loop_control()` 没有编码器时整段跳过**，只保留限幅。
不能让它读到 0：闭环会当成三个轮子全堵转，按各自目标值往上补功率。直道上 A/D
对称还看不出来，转弯时两轮目标值不同，会落进不同的增益档（0.3 / 0.6 / 1.2，
档界在 8 和 20），把原本线性的差速非线性放大，还在档界处跳变。

**`POWER_TO_SPEED_A/B/D` 还是他们的 12.0，本车没测。** 这个值是「功率 1000 对应
每 10ms 多少个编码器计数」，取决于编码器线数 × 减速比 × PCNT 倍频，换电机必须
重测。偏大 → 目标永远追不上，闭环顶到上限，车以 44% 冲出去；偏小 → 目标低于
实际，闭环反过来减功率，车比设定的还慢。用 `TEST_MODE 7` 测，**落地带负载测，
不能垫起来空转**。计数是负的说明那一路 A/B 相接反了。

**4. `pid.c` 的 `PID_MAX_SPEED` 从 8191 压到 3604。** 8191 是 100% 占空比；
3604 是 44%，本车 car-spin 实车标定的安全上限，再高会打滑失控。他们现有参数
最大是 `STRAFE_POWER 2200`（27%），全在这条线以下，所以**这个限幅不改变当前
任何动作**，只防止后面把参数调大之后车冲出去。

## 已知风险

按「出问题的可能性 × 排查难度」排的。

**急弯内侧轮可能只嗡不转。** 本车实测起转值 A/D 约 901 counts（11% 占空比）、
B 约 1065（13%）。他们代码没有起转值保护 —— `SPEED_MIN_POWER 100` 只有 1.2%，
远低于实际起转值。算一下：直行分量 `1600 × 0.866 = 1385`，差速是
`correction × 400 / 1000`，`correction` 限幅 1500，所以内侧轮最低
`1385 - 600 = 785` counts = 9.6%，低于 901。

稳态时误差限幅 ±3、`correction = 300 × 3 = 900`，内侧轮 1025（12.5%），刚好
在起转值之上。但微分项（`KD 500`）在误差突变时能把 `correction` 顶到限幅 1500，
那一下内侧轮就掉到 9.6% 以下。症状：急弯时一个轮子不动，车原地打转而不是画弧。
调 `FRONT_LATERAL_RATIO`（400 往下调）或 `PID_CRUISE_SPEED`（1600 往上调）。

**误差增益极陡。** `err = offset / (crop_w × 0.12 / 6)`，480 宽时除数是 9.6 —— 
偏离中心 9.6 像素误差就是 1.0，±29 像素就打满 ±3。而实际扫描区有 96 像素宽
（480 减去两侧各 40% 的边距）。也就是说画面里线稍微偏一点，`correction` 就饱和。
这是他们的原值，他们能跑，先别动；但如果车在直道上蛇形，第一个怀疑对象是这个。

**摄像头是不是同一型号，无法从代码确认。** 他们 `main.c` 里打印的
`JQ-CAM12-720P-V1` 是一句写死的 printf，不是从设备读的。本车这边整个仓库没有
任何地方记过摄像头型号 —— 因为 camera-test 用的是 `EXAMPLE_UVC_PROTOCOL_MODE_AUTO`
（自动协商），从来不需要知道型号。所以这件事只能看摄像头上的丝印，或者用下面
的办法让驱动自己报。

**分辨率是写死的 480×320，本车没验证过。** 他们固定申请这个组合，
[usb_stream 的文档](https://docs.espressif.com/projects/esp-iot-solution/en/release-v2.0/usb/usb_host/usb_stream.html)
说描述符匹配发生在 `usb_streaming_start()`，不支持时只打 warning，**不会自动
退到最接近的分辨率**。想让驱动自己挑并报出来，把 `camera_track.c` 的两个宏改成
`FRAME_RESOLUTION_ANY`，启动后用 `uvc_frame_size_list_get()` 打印支持列表。
注意 `frame_buffer_size` 是按 480×320 估的 120KB，换大分辨率要一起改。

**裁剪窗口在旋转之前，而且锚在左上角。** 这条最容易踩：
`esp_new_jpeg` 的处理顺序是 `解码 → 缩放 → 裁剪 → 旋转`，裁剪以左上角为原点
（[官方说明](https://preview-developer.espressif.com/pr766/blog/2025/09/esp-new-jpeg-introduction/)）。
所以 `clipper.height = 24` 取的是**传感器原始画面最上面 24 行**，之后才做 180° 旋转。
地面要落在那 24 行里，摄像头必须是倒装的 —— `JPEG_ROTATE_180D` 就是这个装法的补偿。

**所以「画面颠倒就删掉 rotate」是错的**（我先前在这里写错了）。删掉旋转不会
把裁剪窗口挪到画面下半部分，裁的还是最上面 24 行；变的只是那 24 行里哪几行权重
最高（扫描权重 `w_y = 100 - img_y*80/8`，`img_y=0` 权重最高）。本车摄像头如果是
正装的，最上面 24 行拍到的是地平线，**调俯仰角救不回来**。正装的话要么把摄像头
物理倒装，要么改成先解码整帧再自己取底部行。

**巡线只看 8 行、中间 96 像素。** 24 行裁剪里实际只扫 8 行；宽度方向两侧各去掉
40%，480 宽只剩中间 96 像素。视野极窄，所以俯角和装配方向必须对。

## 编码器

**已接，已启用**（`USE_ENCODER 1`）。六个脚见上面的引脚表。

它在他们代码里只做一件事：让每个轮的实际转速跟上给定功率。**没有里程累积**，
所有避障和推球动作还是纯计时（`LEFT_MOVE_MS 900`、`FORWARD_MOVE_MS 700` 等）。
所以它买到的是电池掉压免疫 + 电机个体差异自动补偿，后者本车已经用手工配平
（`MOTOR_TRIM_A 90 / D 100`）付过账了 —— 闭环接上之后这两个配平值可能需要回调，
因为闭环会自己补掉个体差异，配平再叠一层就补过头了。

PCNT 配的是 A 相边缘 INCREASE/DECREASE + B 相电平 KEEP/INVERSE，等于 2 倍频且
能测方向，1000ns 硬件毛刺滤波，10ms 采样，`SPEED_SMOOTH_ALPHA 0.7f` 一阶平滑。

还欠两件事：

1. **`POWER_TO_SPEED_A/B/D` 没标定**，还是他们的 12.0。用 `TEST_MODE 7`，
   落地带负载测。
2. **两个物理确认**（我只能从代码和文档判断，没法替你量）：
   - GPIO17 原来接 ADC。如果只是根杜邦线，拔掉就行；**如果焊了分压电阻，
     那是条低阻通路，会把编码器信号拉坏，还可能超 3.3V。** 拔掉后用万用表量
     17 对 GND 和对 3.3V，都应该是高阻；量到几 kΩ 说明分压电阻还在板上。
   - GPIO39/40 是 `car-spin` 那版超声波的 ECHO/TRIG。现在超声波已经挪到
     18/11，但**39/40 上如果还留着旧杜邦线，会和 A 轮编码器打架**。而且
     `car-spin/README.md` 提醒过 5V ECHO 要分压 —— 如果当初真焊了分压电阻在
     39 上，同样要拆。

   B 轮编码器其实可以牺牲：巡线时 `motor_B_power` 恒为 0，B 的闭环没有意义。
   实在缺脚就把 17/3 让出来，只留 A 和 D 两路，四个脚够。

## 测试顺序

0. **`TEST_MODE 8`（当前默认），先把启动崩溃解决掉。** 接 UART 口看日志，
   找最后一个 `[n/9]`。九步全过就手拨三个轮子，确认编码器计数跟着变、
   方向符号对。这一步不通，后面都是白搭。
1. **轮子悬空**，看 monitor。确认摄像头出图（`http://192.168.4.1:8080`）、
   俯仰角朝下、超声波距离随手掌变化。
2. **还是悬空**，`TEST_MODE 3`，把黑胶带在摄像头前左右移动。看 `误` 的符号：
   线偏右 `误` 应该为正，同时 `A` 和 `D` 出现差值。符号反了立刻停，别落地。
3. **直线段**。只看能不能走直。蛇形就降 `PID_KP`，冲出去就降 `PID_CRUISE_SPEED`。
4. **弯道**。转不够升 `PID_KP` 或 `FRONT_LATERAL_RATIO`；一个轮不转看上面的
   起转值那条。
5. **障碍物**。手在超声波前晃到 5cm 内（模式 3），确认走完左移-前进-右移。
   三个时长（`LEFT_MOVE_MS` / `FORWARD_MOVE_MS` / `RIGHT_MOVE_MS`）只能在赛道上量。
6. 改回 `TEST_MODE 6`，跑完整流程。
