# camera-claude

ESP32-S3 + USB 摄像头 + 三轮全向底盘的巡线小车。从 camera-test 的 `db8fc2d`
提交重构而来，控制逻辑整个换掉了。

当前范围只有两件事：

1. 靠摄像头巡黑线走到障碍物前
2. 超声波连续两次读到小于 10cm 就停车，然后走硬编码的「左移 - 前进 - 右移」

T 型口停车还没做。

## 为什么重写

原来的做法是从画面里预测弯道（顶点在哪、出弯支路朝哪），然后开环转一个固定
角度。全向底盘没有码盘、又受静摩擦限制，开环转角这件事本身就做不准，于是就得
不停加门控去兜住它转不到位的情况 —— pending 窗口、消失确认、弯后对齐、hold
计时器，滚到 3300 行，参数互相打架。

现在不预测弯道。整个问题只剩两个测量和两个比例项：

| 测量 | 从哪来 | 驱动什么 |
| --- | --- | --- |
| `lateral` | 近处扫描带的黑色质心相对画面中心的偏移 | 车体**横移** |
| `heading` | 远处质心减近处质心（线在画面里的倾斜） | 车体**转向** |

弯道就这样被顺带解决了：左转 90° 时，远处那条扫描带落在横向的胶带上，`far_x`
被拉到左边，`heading` 变成大负数，`turn` 自然就是左转。不需要「识别弯道」这个
步骤，也就不需要为它做状态机。

`heading` 用远减近而不是远减中心，是因为车与线平行但整体偏右时，远近两点都偏
右，相减为零，只出平移指令。若用远减中心，车会转过去、越过线、再转回来，来回振。

## 文件

| 文件 | 行数 | 作用 |
| --- | --- | --- |
| `main/line_detect.c` | 117 | 两条扫描带求黑色质心，带一个跨帧搜索窗口 |
| `main/line_control.c` | 66 | 比例控制律，赛道上要调的参数都在 `.h` 里 |
| `main/line_mixer.c` | 78 | kiwi 三轮混控，整向量缩放 + 起转值处理 |
| `main/line_follow.c` | 649 | 电机驱动、状态机、超声波、TFT 叠加层 |
| `main/camera_display.c` | — | UVC 取流 + JPEG 解码 + 自适应阈值（沿用原版） |
| `main/ultrasonic.c` | — | HC-SR04，带超时（沿用原版） |

前三个是纯 C，不含 ESP 头文件，所以能在 PC 上跑回归测试。

搜索窗口是 `line_detect.c` 里唯一的跨帧状态：质心只在上一帧位置附近找。这
一条就够挡掉桌腿、障碍物木板这类画面里的其他暗块，不用再写别的过滤。丢线时
窗口逐帧变宽，避免车稍微偏一点就永远找不回来。

## 状态机

```
WAIT ──连续 3 帧看到线且过了 600ms──> FOLLOW
FOLLOW ──丢线──> SEARCH ──原地按最后转向方向旋转──> 找到回 FOLLOW
                        └──超过 5s 没找到──> STOPPED
FOLLOW ──超声波连续 2 次 <10cm──> BRAKE -> AVOID-L -> AVOID-F -> AVOID-R -> FOLLOW
```

避障那四步完全按时间走，不看摄像头。走完后有 900ms 的重捕获窗口，这段时间丢线
只直行不旋转，免得刚回到线上就被判成丢线转起来。

弯道顶点走到车底下时线确实不在画面里，所以 SEARCH 不是故障态，是巡线的一部分。

## 调参

参数分四组，按顺序调。全部在 `main/line_control.h` 和 `main/line_follow.c` 顶部。

**1. 速度**（`line_control.h`）
```c
#define LINE_FORWARD_CRUISE 22   // 直道
#define LINE_FORWARD_CORNER 15   // 弯道
```
冲出弯就降 CRUISE。走不动就升，但别超过 44（PWM 上限）。

**2. 增益**（`line_control.h`）
```c
#define LINE_GAIN_YAW 45   // turn = -GAIN_YAW * heading / 1000
#define LINE_GAIN_LAT 55   // lat  = +GAIN_LAT * lateral / 1000
```
转弯转不够就升 YAW，来回振就降。误差单位是画面宽度的千分之一，所以换分辨率
（160x120 / 120x80）不用重新调 —— 这一点由回归测试钉住。

**3. 死区**（`line_control.h`）
```c
#define LINE_DEADBAND_HEADING 30
#define LINE_DEADBAND_LATERAL 45
```
直道上左右小幅抖动就升。

**4. 避障时长**（`line_follow.c`）
```c
#define AVOID_LEFT_MS 1600U
#define AVOID_FORWARD_MS 1800U
#define AVOID_RIGHT_MS 1600U
```
左移不够就加 LEFT_MS。这三个只能在赛道上量。

硬件校准值（GPIO、起转值 11/13、PWM 上限 44、配平 90/100）来自 car-spin 的实车
标定，不要动。

## 屏上调试

TFT 会画出检测器看到的东西：

- 青色横线 = 两条扫描带的上下边界
- 黄色竖线 = 搜索窗口边界
- 绿色竖线 = 近处质心（驱动横移）
- 红色竖线 = 远处质心（驱动转向）
- 三行文字 = 状态/ARM、lat/hd/阈值、f/t/l/距离

绿线没落在胶带上就是阈值问题。黄线框住了别的暗块就是窗口太宽。

## 阈值校准

黑胶带和白板对比度极强，为什么还会认错？因为难的不是"区分黑白"，是"选一个数
让它在整幅画面每个角落同时成立"。摄像头动态范围有限，画面四角比中心暗一截
（暗角），自动曝光又会随视野里黑色多少来回调整，于是能分开中心胶带的那个数，
到了画面边缘就把白板也判成黑。

### 计算链

```
ROI（高度 35%~100%，宽度 10%~90%，隔行取样）
  -> 亮度直方图
  -> dark  = 第 2 百分位     light = 第 90 百分位
  -> 若 light - dark < 32，返回 0（对比度守卫）
  -> thr = dark + (light - dark) × 45%
  -> 限幅 [45, 160] -> 每帧最多变 6 -> EMA 3:1
```

ROI 上沿是 35%，刻意对齐远带上沿 38%。**不要往上抬**：抬到 15% 会把远处的墙和
房间统计进去，房间暗则 light 被拉低（胶带不再算黑），背后有窗则 light 被抬高
（白板整片算黑）。同一条赛道换个位置就不行，多半是这个。

### 看 log，不要靠眼睛

`idf.py monitor` 每 300ms 一行：

```
FOLLOW armed=1 lat=+12 hd=-45 fill=140/95 thr=88 lum=38/196 f=20 t=+2 l=+1 abd=-18/0/20 dist=45.3
```

`lum=dark/light` 是直方图那两个原始百分位，`fill=近带/远带` 是暗像素千分比。
**校准时先看 lum**，只看最终 `thr` 分不清"胶带反光"和"曝光乱跳"。

健康的数字：`lum` 大约 `30~60 / 170~220`，`thr` 60~110，近带 `fill` 80~250‰。

近带 `fill` 该是多少可以算：近带约 12 行 × 窗口约 72 列 ≈ 864 个取样点，胶带占
窗口宽度约 1/6，所以 ~130‰。

### 对照表（一次只改一个）

| log 现象 | 真因 | 动作 |
| --- | --- | --- |
| `thr=0` | 对比度守卫触发 | 看 `lum` 差值。差值小就是光照问题，先加光，别急着降 `MIN_CONTRAST` |
| `lum` 的 dark > 80 | 胶带没进 ROI，或胶带反光 | 先确认摄像头俯角；亮胶带（有光泽）换哑光的 |
| `lum` 的 light < 120 | 整体太暗 | 加光。降阈值治不了，噪声会跟着进来 |
| `thr` 正常但近带 `fill < 12` | 阈值偏低，胶带没算成黑 | `BLACK_FRACTION_PERCENT` 45 → 55 |
| 近带 `fill > 600` | 白板被判成黑 | `BLACK_FRACTION_PERCENT` 降回；**别抬 `THRESHOLD_MIN`** |
| 没胶带时 `thr` 漂到 100+ | 第 2 百分位取到了白板 | 设计局限，靠搜索窗口兜，不用改 |
| `thr` 逐帧跳动大 | 平滑不够 | `THRESHOLD_SLEW` 6 → 3 |

有光泽的电工胶带在顶灯下会出现镜面高光，局部亮度能到 200 以上，那一块黑胶带在
画面里是白的。这一条不是参数能解决的，换哑光胶带。

## 烧录与测试

```powershell
cd esp-projects\camera-claude
idf.py set-target esp32s3
idf.py build
idf.py -p COM3 flash monitor
```

`set-target` 只有第一次需要（它会重建 sdkconfig）。COM 口在设备管理器里确认。
退出 monitor 是 `Ctrl+]`。

VS Code 里用 Espressif IDF 扩展也行：底栏选好串口和 esp32s3，然后
「Build, Flash and Monitor」那个火焰图标。

**测试顺序（别跳）**

1. **不放地上，手拿着车**。电机在确认到线之前不会上电（连续 3 帧 + 600ms），
   但拿在手上更保险。看 monitor 里的 `lum` 和 `fill`，按上面的对照表把阈值调好。
   这一步不过，后面全是白费。
2. **车轮悬空**，把胶带在摄像头前左右移动。看 `lat` 符号：胶带偏右 `lat` 为正，
   同时 `l` 应该为正、`abd` 三个数都非零。符号反了立刻停，别放地上。
3. **直线段**，50cm 那段。只看它能不能走直。冲出去就降 `LINE_FORWARD_CRUISE`，
   来回蛇形就降 `LINE_GAIN_LAT`。
4. **90° 直角弯**。转不够升 `LINE_GAIN_YAW`，转过头降。
5. **起点那个 120° 锐角弯**。这里预期会不顺 —— 见下面「已知问题」。
6. **障碍物**。用手在超声波前晃到 10cm 内，确认它进 BRAKE 然后走完左移-前进-右移。
   避障时长（`AVOID_*_MS`）只能在赛道上量。

摄像头断流超过 1200ms 会自动断电停车，所以拔 USB 是安全的急停。

## 已知问题

**起点后的 120° 锐角弯处理不了。** 几何上出弯支路在画面里朝右下方走（往车身
底下去），远带看不到它，近带会同时看到进弯线和出弯线两个黑块。所以 `heading`
不会像 90° 弯那样干脆摆过去，车大概会先丢线，然后靠"按最后方向原地旋转找线"
兜底转过去。方向是对的（默认往右），但转速够不够、能否在 5s 内重新看到线都不
确定。90° 直角弯反而是最有把握的。

**视觉层没有重写。** `camera_display.c` 的自适应阈值沿用原版，只对齐了 ROI、
放宽了上下界、加了 `lum` 诊断。如果历史失败的真因在阈值，控制层重写治不到，
所以测试顺序第 1 步是阈值而不是跑赛道。
