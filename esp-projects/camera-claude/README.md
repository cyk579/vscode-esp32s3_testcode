# camera-claude 本车复现版

2026-09-06 按 `引脚对应表2.xlsx` 核查。默认 `TEST_MODE=6`，运行原组完整流程：摄像头巡线/避障、绿球、红球。要单独复现本组的巡线避障，可在 `main/main.c` 选模式3。用户要求停用找球的另一份工程是 `VScode ESP`，该工程已单独切为只运行巡线避障。

原始参考是 `../camera-other_group`，保持不变。本次修复了之前移植中导致运行效果不等同于原组的配置问题。

## 本次修复

- LCD CS 从 GPIO47 改为已确认的 GPIO0；实物也必须改线。
- `TEST_MODE` 从8（诊断）恢复6（原组完整模式）。原来的诊断模式7/8保留，默认不执行。
- `pid.c` 补入 `board_pins.h`。之前 `USE_ENCODER` 只在编码器文件可见，PID 编译单元看不到它，因而实际跳过速度闭环；现在两处开关一致，启用原组闭环。
- `PID_MAX_SPEED` 从移植版的3604恢复原组8191。它是13位PWM上限，不是巡航占空比；巡航、PID、避障和推球常量仍用原组数值。
- 修正关于GPIO45/46、JTAG、编码器倍频及闭环累加的旧注释。默认弱下拉不等于永远只能为低；当前PCNT是A相双边沿、B相判向的2倍频；速度修正不是把上一周期输出一直累加到满量程。

预处理检查确认：当前模式6的主程序和启用编码器后的PID，与 `camera-other_group` 相应代码的有效token完全一致。仍保留必要的硬件适配：集中引脚、GPIO8 STBY、工程/板级配置，以及已有的编码器采样任务2048字节栈（原组1024）。

## 接线

`main/board_pins.h` 是唯一的外设引脚定义文件。下表均是GPIO号。

| 外设 | 本车 | 原组 |
| --- | --- | --- |
| A轮 PWM / IN1 / IN2 | 9 / 12 / 10 | 4 / 6 / 5 |
| B轮 PWM / IN1 / IN2 | 4 / 6 / 5 | 9 / 11 / 10 |
| D轮 PWM / IN1 / IN2 | 16 / 7 / 15 | 40 / 42 / 41 |
| STBY | 8 | 无软件控制 |
| A编码器 E1A/E1B | 39 / 40 | 7 / 15 |
| B编码器 E2A/E2B | 17 / 3 | 12 / 13 |
| D编码器 E4A/E4B | 41 / 42 | 2 / 1 |
| 超声 TRIG / ECHO | 18 / 11 | 3 / 14 |
| 舵机 水平 / 俯仰 | 1 / 2 | 8 / 18 |
| TFT MOSI / CLK / CS / DC / RST | 14 / 13 / **0** / 21 / 38 | 21 / 47 / 48 / 17 / 16 |
| USB D- / D+ | 19 / 20 | 固定相同 |
| UART0 TX / RX | 43 / 44 | 系统默认 |

本车 A右前、D左前、B后轮。不要根据两个组里相似的GPIO号对应轮子，必须按本车接头名称接线。`USE_ENCODER` 当前定义为1，六根编码器信号均需要实际接上。若以后不用编码器，应注释/删除整个宏定义；这里沿用 `#ifdef` 开关，写成0仍视作已定义。

**把LCD的CS线从47移到0。** WROOM-2的47/48为1.8V域，之前能显示不代表电平合规。GPIO0正常复位须为高，LCD端不能下拉或主动拉低，可约10kΩ上拉至3.3V。GPIO3与39~42的JTAG限制、GPIO资源余量及其他电气问题见根目录核查说明。

红外OUT1..4在新表中为空，不能再保留旧的41/42/2/1连接。`track.c` 保留编译保护，阻止误切到会与编码器、舵机冲突的红外模式。驱动板ADC也没有分配，尤其不要再接占用为E2A的GPIO17。

## 构建

原组只有组件源文件，没有提供他们的完整板级 `sdkconfig` 或依赖锁文件。本目录使用本仓库已记录的WROOM-2-N32R16V板级配置：32MB OPI Flash、Octal PSRAM、80MHz、240MHz CPU。

在 ESP-IDF 终端进入本 README 所在目录，然后：

```powershell
# 使用新的构建目录，避免沿用旧电脑缓存。
idf.py -B build-local set-target esp32s3
idf.py -B build-local build
idf.py -B build-local -p COM5 flash monitor
```

COM5替换为实际UART串口。`set-target`会重建本工程sdkconfig；如果以后手动调过其他选项，先保存该配置。首次构建会解析并下载 `usb_stream` / `esp_new_jpeg`，此目录未得到原组组件版本锁，无法保证下载版本与他们一致。

摄像头启用后原生USB口与GPIO19/20复用，持续日志走UART0（43/44）。本次没有烧录或修改eFuse，也未改变欠压检测档位来处理供电问题。

## 明天先检查这些

1. 架空确认屏幕和三路电机转向，再确认编码器接线。模式6可能在取得有效图像之前驱动电机，不能把“摄像头未连接”当作停止条件。
2. 原程序没有完整的摄像头断流停车处理。电源开关作为急停，拔摄像头不保证停车。
3. 相机请求480×320、25fps；附带相机说明图标为JQ-CAM12-720P-V1，但支持的具体UVC格式仍以枚举/运行日志为准。VScode ESP使用480×320、15fps，两组请求的帧率不同。
4. 初始舵机水平0°、俯仰+30°。画面要朝向地面；软件参数相同不能保证安装极性、镜像方向相同。保留原组的裁剪与180°旋转，不据此猜改视觉算法。
5. TFT保留原组128×160竖屏、`MADCTL=0xC8`、偏移(2,1)、SPI 10MHz。字库不完整，缺字不是引脚失效；该组TFT显示距离和编码器数值，不显示摄像头画面。

摄像头预览使用程序自带热点 `ESP32_CAM`（密码 `12345678`），浏览器访问 `http://192.168.4.1:8080`。

若出现此前记录过的反复重启，可临时用模式8获取UART日志。模式8会改变启动时序、包含异步任务，某个步骤的“OK”只代表函数返回/任务已创建，不能据最后一条日志直接断定是哪一步崩溃。结合复位原因、panic/backtrace、PSRAM初始化与供电检查判断。模式7是会驱动电机的编码器标定，手动使用时需留出可控活动空间。
